## 4. 为什么这趟落地只有 3.73 m：FIN 段是【缩小】而不是放大

| log | gfold 末 `dist`/`vh` | 落地 `dist`/`vh` | 放大倍数 |
|---|---|---|---|
| 195348 | 1.34 / 1.75 | **11.54** / 3.60 | **dist ×8.6** |
| **224134** | 1.53 / 0.88 | **3.73** / 1.68 | **dist ×2.4** |
| 212521 | 10.11 / 0.86 | 5.07 / 1.15 | dist ×0.5 |

**195348 的 FIN 段把误差放大了 8.6 倍**（1.34 → 11.54），这是那趟落地差的直接原因。

224134 的 FIN 段虽然也放大了 2.4 倍，但起点更小，所以结果更好。

### 4.1 FIN 段逐帧对比

| | 195348 `fin_ah` | 224134 `fin_ah` |
|---|---|---|
| 峰值 | **3.33** m/s² | **1.95** m/s² |
| `vh` 峰值 | **5.27** m/s | **3.01** m/s |
| `tilt_cmd` 打满 8° 的帧 | 5/14 | **0/18** |

**195348 的 `fin_ah` 需求是 224134 的 1.7 倍，把 `vh` 推到 5.27，导致 `dist` 从 1.34 涨到 11.54。**

FIN 段 `FIN_VH_KP=0.35` 分量独立 P-D 的老问题还在（`HANDOFF.md §10.13`），
只是这趟 `vh` 起点更小，没被推到发散的边上去。

## 6. 那 224134 为什么起点更小

`dist0` / `vh0` 由【kOS 侧终端制导】决定，不是 kRPC 侧能控制的。

| log | `dist0` | `vh0` |
|---|---|---|
| 202734 | 21.88 | **17.80** |
| 190025 | 26.67 | 15.81 |
| 144058 | 16.23 | 11.59 |
| 135036 | 17.57 | 8.24 |
| 154351 | 13.79 | 5.79 |
| **224134** | **3.61** | **3.08** |

`vh0` 从 17.80 一路降到 3.08 —— **跨度 5.8 倍**。
这说明 kOS 侧的终端精度本身波动很大，**这是可以改进的方向**（比改 kRPC 侧增益有意义）。

## 7. 结论

```
问：224134 没问题，是巧合吗？

答：不是巧合，是初始条件好。

  1. 三趟代码完全相同（155 列，无 az_reject）
  2. 极限环还在：频率 4.2 s 一模一样，只是振幅从 10.0 衰减到 3.99
  3. dist0 = 3.61 m / vh0 = 3.08 m/s，都是历史最小
  4. FIN 段放大 2.4 倍（195348 是 8.6 倍），因为 vh 起点小

  换句话说：症状减轻了，病根没去。
  下一趟如果 vh0 回到 10+，同样的代码还会出问题。

  证据：corr(vh0, distL) = 0.887，corr(dist0, distL) = 0.867
        而 corr(azE50, distL) 只有 0.379
```
