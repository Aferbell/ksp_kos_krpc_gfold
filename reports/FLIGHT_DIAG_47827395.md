**全程没有任何客户端连接记录。** kRPC 会把连接写进日志，所以这不是"连上但被拒"，
而是**`gfold_land.py` 在飞行期间根本没有运行**（或运行了但没连上）。

另外 `log-B1040-9-gfold/` **是空的**（只有 README.md）——

```cfg

```

所以**不是配置问题**。

### 怎么修

飞行期间必须让 `gfold_land.py` 一直运行。建议流程：

1. **先启动 KSP 并进入飞行场景**（载入存档 / 在发射台）
2. **再开一个 PowerShell 窗口**，启动监听程序：
   ```powershell
   cd "D:\SteamLibrary\steamapps\common\Kerbal Space Program\Ships\Script\dev\krpc"
   python gfold_land.py
   ```
   成功时应立刻看到：
   ```
   [conn] 127.0.0.1:50000 …
   [conn] server version = 0.6.0
   [wait] 等待交班门（kOS 段1 正在飞行）…
   ```
   看到这三行 = 连上了。**没看到 `[conn] server version` 就是没连上。**
3. **然后**在 KSP 里跑 `B1040-9.ks`

**顺序很重要**：程序必须先连上并进入 `[wait]`，再让火箭起飞。
如果先跑 kOS 脚本、火箭都飞一半了才启动程序，程序会从当前状态开始等门，
很可能门已经错过了。

**自检**：程序打印 `[conn] server version = 0.6.0` 就说明链路通。
如果卡在 `[conn]` 不动 → 服务器没开（游戏内点 kRPC 图标 → Start Server）。

## 问题②：kOS 段1 律失效 —— 竖直指令贴在下限

### 证据（从 `land_log_47827395.csv` 统计）

| 量 | 实测 | 判据 |
|---|---|---|
| `acmd_up` 中位数 | **−4.80 m/s²** | 而 `−0.5g = −4.91` ⇒ **全程贴着下限** |
| `acmd_h` 中位数 | **30.00 m/s²** | = `lat_budget` ⇒ **横向长期饱和** |
| `vh` 最小值 | **52 m/s** | 从没降下来（应收到接近 0）|
| `dist` 最小值 | 25 m | 收到 25 m 后**反弹到 188 m** |
| 触地 | `vz=−55 / vh=180 / tilt=61°` | 坠毁 |

### 根因（已数值复现，与日志完全吻合）

我在 `.ks` 里写的是"两级律"，其中第二级把
`sqrt(2·a_b·|r_go|)` 当成了**期望速率（设定值）**：

```
alt=4092 / dist=2533 / a_b=30.3
  |r_go| = 4782 m
  |v_tgt| = sqrt(2*30.3*4782) = 539 m/s        <- 这个数是"能刹住的上限"
  v_target(3) = -539 * (4055/4782) = -457 m/s
  实际 vz = -330  =>  误差 = -127  =>  /0.8 = -158
  被 -0.5g 下限夹住 => a_v = -4.85
```

**推算值 −4.85 与日志实测的 −4.84 完全一致** ⇒ 根因确认。

**概念错误**：`sqrt(2·a·d)` 是"从该速度起、在距离 d 内以 a 刹停"的**速度上限**，
不是"应该有的速度"。把它当设定值，就变成"命令火箭加速下冲到 457 m/s"，
与意图相反。竖直通道因此几乎不出力（一直 −4.8），横向被配额钉在 30 饱和。

### 一个更深的结论

这次实飞还暴露出：**任何用多项式项闭位置的律都不可行**（独立核算）：

| 律 | 需要 | 实际可用 |
|---|---|---|
| 四次多项式 | `T ≥ 81.6 s` | 燃料只够 ~20.8 s |
| 二次型位置项（ZEM/ZEV 形式） | `tgo ≥ 58.6 s` | 同上 |
| 位置项在 tgo=21 s 时的幅值 | `231 m/s²` | `a_net = 47` |

⇒ 位置**必须靠推力方向闭合**，不能用位置项。这个结论现在有三处独立证据。
