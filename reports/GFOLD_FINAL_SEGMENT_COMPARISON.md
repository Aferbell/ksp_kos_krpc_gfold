## 2. 问题 1（已修）：油门被覆盖 —— 结构差异

### 2.1 参考仓库的写法

```python
# demo3_gfold.py
elif nav_mode == 'final':                                    # 413
    vessel.control.throttle = clamp(lerp(...))               # 420  <-- 直接写油门
    target_direction = ...                                   # 425-427
# 【final 分支到此结束，不调用任何"写油门"的函数】
...
if n_i > 0:
    vessel.control.throttle = target_throttle                # 405  <-- 这属于 gfold 分支
```

### 2.2 本项目的写法

```python
else:                                                        # 2145 final 分支
    thr = _clamp(_lerp(...), 1.0, 0.05)                      # 2154
    self.v.control.throttle = thr                            # 2155  <-- 写了
    self.thr_cmd = thr                                       # 2156
    ...
    target_a = td * a_cap       # 原实现（错）                # 2182
    self.apply(target_a, target_direction, game_dt)          # 2187  <-- 又写一次
```

`apply()` 内部（1556-1561）：
```
throttle = ||target_a|| / a_cap
         = ||td * a_cap|| / a_cap  =  a_cap/a_cap  =  1.0     <-- 恒为 1
```

⇒ **2154-2156 算出的油门在同一帧被 2187 覆盖，成为死代码。**

**这台移植把 `apply()` 加进 final 分支，才引入该覆盖**（参考仓库 final 分支没有这一步）。

### 2.3 修复与验证

```diff
- target_a = td * a_cap
+ target_a = td * thr * a_cap
```

让 `target_a` 的**幅值**承载 `thr`，则 `apply()` 复算的 `|target_a|/a_cap` 恰好还原它。

离线仿真（从真实入口 alt=226.3 / vz=−74.11 / m=153 t 出发）：

| | 步 0 | 步 8 | 终态 |
|---|---|---|---|
| 修复前 | alt 215.7 vz −66.3 | alt 176.4 vz **−2.7** | vz **+659**，未触地 |
| 修复后 | alt 214.3 vz −75.2 | alt 114.8 vz −72.9 | **alt 36.5 vz −2.01，触地** |

修复前**精确复现日志现象**（`vz` 由负转正）。

## 3. 问题 2（已修）：`tilt_dir_cmd` 在 final 段是陈旧值

### 3.1 现象

帧 45-53（**整个 final 段**）：`tilt_dir_cmd` **恒为 7.70**，
而同期 `a_cmd_h` 在 **0.55 ~ 24** 之间大幅变化。
一个"姿态目标"不可能同时给出恒定倾角和变化的水平指令。

### 3.2 根因

`tilt_dir_cmd` 此前**只在 `track()`（gfold 分支）里赋值**（原 1392-1396 行）。
final 分支**从不更新它** ⇒ 日志把进入 final 前最后一帧的旧值一路打印。

### 3.3 修复

挪到 `apply()`（line 1635）—— 这是 **hold / gfold / final 三个分支共同的出口**，
`target_direction` 在此已定稿，因此该列必定反映"本帧真正命令的姿态方向"。

已验证三个分支都调用 `apply()`（2101 / 2235 / 2244 行）。

## 4. 结合载具真实数据的分析

### 4.1 不是能量问题

进入 final 时（帧 45）：alt=226.3、vz=−74.11、m≈153 t

```
a_cap = 58.76, a_net_max = 48.96 m/s^2
满推力停车距离 = 74.11^2/(2*48.96) = 56.1 m
可用高度       = 189.5 m        => 余量 133 m，【完全够】
```

### 4.2 自杀点火触发点分析

`frac > 0 ⟺ est_h_low < 0 ⟺ e0 < vz²/(2*max_acc_low)`

| vz | 触发高度 e0* |
|---|---|
| −80 | 86.0 m |
| −74 | 73.8 m |
| −60 | 48.4 m |
| −40 | 21.5 m |

进入 final 时 e0=189.5 ≫ 73.8 ⇒ `thr=0.05`（**"还高，先滑行"**）—— **合理**。

### 4.3 但发现一个**值得注意的行为**

从修复后的仿真看，final 段在 189→151 m 之间**继续滑行并加速**：
`vz` 从 −74.11 恶化到 −80.70，然后才开始点火。

| 步 | alt | vz | thr |
|---|---|---|---|
| 0 | 226.3 | −74.11 | 0.050 |
| 3 | 189.7 | −77.41 | 0.050 |
| 6 | 151.5 | **−80.70** | 0.281 |
| 9 | 114.8 | −72.94 | 0.638 |
| 24 | 36.8 | **−2.00** | 触地 |

**这是该律的设计行为**（等重力把速度"喂"到触发点再点火），
最终触地 `vz=−2.00`，符合 `term_v=2.0`。
⇒ **律本身可用**，但**它不跟踪规划轨迹**，是纯 suicide burn。

### 4.4 对 6% 推力偏差的敏感性

已知 `a_cmd_mag/(thr_cmd·T/m) = 0.9402` ⇒ 实际推力疑为 ~8.45 MN（配置 8.99 MN）。

| 假设推力 | e0* (vz=−74) | 满推力停车距离 |
|---|---|---|
| 8.99 MN（配置） | 73.8 m | 56.1 m |
| 8.45 MN（反推） | 79.8 m | 60.4 m |

⇒ 差约 6%，**不改变结论**，但会让点火点偏晚 6%。
**建议**：按原建议在日志加同帧 `self.v.max_thrust`，下次即可判定。
