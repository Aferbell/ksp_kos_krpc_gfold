## 1. 找到了：一行移植错误

### 参考仓库原文（`dev/gfold/demo3_gfold.py` line 378-379）

```python
target_a  = u_i  + (v_i  - vel) * k_v + (x_i - error) * k_x
target_a_ = u_i_ + (v_i_ - vel) * k_v + (x_i - error) * k_x
                                        ^^^ 两个都是 x_i ！
```

### 我的实现（改之前）

```python
target_a_ = u_i_ + (v_i_ - vel) * K_VEL + (x_i_ - error) * K_POS
                                          ^^^^^ 用了 x_i_ 【错误】
```

**`target_a_` 是驱动姿态的向量**（`target_direction = target_a_/|target_a_|`），
所以这个错误直接决定了火箭朝向。

### 为什么致命

`x_i_` 是**前瞻 `step` 个节点**后的位置：

```
step = min(1.5·N/tf, |vel|/50·N/tf)
     = min(1.5×80/19.75, 360/50×80/19.75) = min(6.08, 29.2) = 6.08 节点
     = 1.5 s
```

本项目入口 `vz ≈ −290 m/s` ⇒ **前瞻点比当前低 290×1.5 ≈ 435 m**
⇒ `(x_i_ − error)[0] ≈ −435` ⇒ `K_POS` 项 = `0.5×(−435) = −218`

**实测**（`dev/krpc/diag_tad.py`，用真代码打印）：

| step | `ta_wrong` 原始值 | 经 conic_clamp 后 |
|---|---|---|
| 0 | `[−200.7, +55.5]` | `[2.5, 0, 0]` ← **纯竖直** |
| 1 | `[−137.5, +52.6]` | `[2.5, 0, 0]` |
| 2 | `[−156.0, +78.9]` | `[2.5, 0, 0]` |
| 3 | `[−180.5, +80.0]` | `[2.5, 0, 0]` |
| 4 | `[−202.7, +73.3]` | `[2.5, 0, 0]` |

**竖直分量全为负 ⇒ `conic_clamp` 走 `a_ver<0 → a_ver=0 → cap_hor=0` ⇒ 返回纯竖直。**

### 日志铁证

新增的 `tilt_dir_cmd` 列（= `target_direction` 的真实倾角）：

```
tilt_cmd      中位 0.00    max 86.66     ← 节流向量（tilt_cmd 是它）
tilt_dir_cmd  中位 0.00    max 90.00     ← 姿态目标【全程 0】
tilt_act      中位 15.88   max 133.72
```

**`tilt_dir_cmd` 全程 0.00 ⇒ 姿态被命令"指向天顶"**，
而 `tilt_cmd` 说 76°。**火箭完全照指令做（保持竖直），但指令本身是错的。**

### 一级为什么不跟踪（完整因果链）

```
target_a_ 误用 x_i_
  → 竖直分量 −200
  → conic_clamp 返回纯竖直 [2.5, 0, 0]
  → tilt_dir_cmd = 0°  ⇒ 姿态被命令竖直
  → 竖直推力 = thr·a_cap·cos(0°) ≈ 40 m/s²（而轨迹只要 9.5）
  → 本机猛减速（vz −278 → −262）
  → 速度误差累积 (v_i−v)[0] → −16.9
  → K_VEL 项 = −13.5 压过 u_i[0]=9.9
  → target_a[0] 变负 → conic_clamp 清零水平
  → a_cmd_h = 0.00  ⇒ 【横向不跟踪】
```

### 修正效果（`diag_tad.py` 实测）

| step | tilt_cmd | 修正前 `tilt_dir_cmd` | **修正后** |
|---|---|---|---|
| 0 | 75.37 | 0.00 | **78.98** |
| 1 | 1.86 | 0.00 | **28.92** |
| 2 | 6.24 | 0.00 | **27.15** |
| 3 | 41.65 | 0.00 | **43.62** |
| 4 | 46.50 | 0.00 | **46.50** |
| 5 | 36.45 | 0.00 | **0.58** |

**姿态目标终于跟随轨迹了。**

### 为什么参考仓库没暴露

它的用例入场高度低（1.1 km）、横速小、`tf` 短 ⇒ `step` 小
⇒ `(x_i_ − error)` 不会到 −435。
本项目的大垂速把 `step` 放大到 1.5 s，才让这个错误显形。

## 2. 优化一：默认关闭重解（按你的要求）

### 改动（`dev/krpc/gfold_land.py`）

```python
# 前：default=2.0（每 2 s 重解一次）
# 后：
ap.add_argument('--replan-dt', type=float, default=0.0,
                help='重解周期 [s]；0 = 不重解（默认），只跟踪最初轨迹。')
```

判据加了 `self.args.replan_dt > 0.0` 前置，`0` 即彻底不重解。

### 依据（日志验证）

每次重解都让 `a_cmd_h` 跳变：

| 重解 | 跳变 |
|---|---|
| #2 | 39.67 → **0.00** |
| #3 | 41.04 → **0.00** |
| #4 | 42.91 → **0.00** |
| #5 | 44.59 → **0.00** |

重解本身引入两个扰动：
1. 新轨迹起点用**外推状态**，与本机总有偏差
2. `_collect_resolve` 把 `gfold_n_i` 重置为 −100 ⇒ 索引重新定位 ⇒ 采样点跳变

**⇒ 求解已快到 0.17 s、单条轨迹质量已验证的前提下，重解是扰动而非精度。**

> 保留该开关：若实测单条轨迹确实跟不上（大扰动/推力偏差），
> `--replan-dt 2.0` 一行即可切回。

## 3. 优化二：减小交接误差（kOS 侧）

### 实测交接延迟

| 趟 | kOS 交班 alt | kRPC 首帧 alt | 差 |
|---|---|---|---|
| 112348 | 5032.6 | 4979.6 | **53.0 m** |
| 120327 | 5034.8 | 4987.7 | **47.1 m** |
| 123550 | 5032.6 | 4979.0 | **53.6 m** |

以 `vz≈−290` 计，**延迟 0.17 s**。

### 原因：放权被压在两次 IO 之后

旧顺序（`boot/B1040-9.ks`）：

```
① 拼 gfold_msg（十几个 round + 字符串拼接）
② print gfold_msg        ← 写终端
③ LOG ... TO 文件        ← 【写盘，最慢】
④ 才 ctrl_main=false + unlock + break
```

**在 ④ 之前，kOS 仍在 `lock` 执行器**，kRPC 即便接管也会被每帧覆盖。
而火箭以 290 m/s 继续下坠 —— 白掉的正是这段时间。

### 修正：把放权提到最前

```
① ctrl_main=false + throttle_demand=0 + unlock ×2 + pilotmainthrottle=0
   ← 【立即交出控制权】
② 再拼字符串、print、LOG   ← 记账不影响控制权
③ phase=3 + break
```

**安全性**：`unlock` 只撤销触发器，后续 `print`/`LOG` 不依赖执行器；
`phase=3` + `break` 仍在同一分支内，行为不变。

**kOS 审计基线保持**：`lock` ×2（行 761/762）、`unlock` ×2+2（行 1236/1237 交班 + 1486/1487 着陆，互斥路径）。
