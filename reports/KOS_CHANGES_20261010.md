## 2. 为什么 kRPC 侧不需要改（方案B 的"删除"变体）

方案B 原本有两种实现：
- **加**：给 kRPC 门补 `vh < 10`
- **删**（用户选择）：把 kOS 门的 `vh < 10` 删掉

**两者等价性（源码核对）**：

| 条件 | kOS 改动后 | kRPC | 是否等价 |
|---|---|---|---|
| 高度上限 | `h_aim < 150` ⇒ **alt < 667** | `alt < GATE_ALT(667)` | ✅ |
| 合速度 | `\|v\| < 120` | `vmag < 120` | ✅ |
| 锥内 | `dist_hz ≤ h_gnd/tan(48°)` | `cone_ok` | ✅ |
| 横速 | **（已删）** | （本来就没有） | ✅ |
| 高度下限 | `h_gnd > 30` ⇒ alt > 47 | `alt > 358` | ⚠️ kRPC 更严（兜底，无害） |

`h_aim` 的几何：`h_aim = alt_radar − target_alt − aim_alt = alt − 17 − 500`，
故 `h_aim < 150 ⟺ alt < 667`，与 `GATE_ALT` **完全一致**。

**⇒ 删除后两门在实用区间完全等价，同时满足、重叠消失。**
kRPC 不必新增等待条件，故**一行都不用改**（比"加"变体更省）。

**唯一残留差异**是高度下限（kRPC 358 更严）。正常情况下载具先经过 alt=667
（两门同时满足），下限永不生效。**无需处理。**

## 5. ★ 解释：kRPC 命令行里时间会突然跳过约 2 秒

**结论：这不是控制循环卡顿，而是控制台打印的抽稀条件写成了"取模"。**

### 5.1 源码

`dev/krpc/gfold_land.py:4223`（唯一一处打印进度的语句）：

```python
if int(tt * 2) % 4 == 0:
    print(f'  t={tt:5.1f} alt={alt:7.1f} dist={dist:6.1f} ...')
```
其中 `tt = time.time() - t0`（自进入主循环起的**墙钟**秒数）。

### 5.2 数学生效区间

```
int(tt*2) % 4 == 0   <=>   tt ∈ [0,0.5) ∪ [2,2.5) ∪ [4,4.5) ∪ [6,6.5) ∪ ...
```

**打印窗口只有 0.5 s 宽，但每 2 s 才开一次。**

于是控制台上看到的是**一阵一阵的**：
```
t= 0.2  0.4  0.5 |  （静默 1.5 s）  | t= 2.1  2.2  2.3  2.4  2.5
                 |                  | （静默 1.5 s）
                 |                  | t= 4.0  4.1  4.3  4.4 ...
```
**最后一行（2.5）→ 下一块第一行（4.0）之间空了 1.5 s，
用户看到 `t` 从 2.5 直接变成 4.0 ⇒ 感觉"跳了两秒左右"。**

### 5.3 实测复现（用真实日志的帧时刻）

脚本 `dev/analysis/explain_console_time_jump.py`：

| 日志 | 日志帧数 | 控制台会打印 | 显示值最大间隔 | 真实帧间隔>0.5s |
|---|---|---|---|---|
| 124409 | 172 | 45 行 | **1.68 s** | **0 次** |
| 125000 | 92 | 24 行 | **1.84 s** | **0 次** |
| 130003 | 97 | 23 行 | **1.83 s** | **0 次** |
| 132420 | 106 | 26 行 | **1.83 s** | **0 次** |

```
124409 控制台实际显示的 t: 0.2 0.4 0.5 2.1 2.2 2.3 2.4 2.5 4.0 4.1 4.3 4.4 6.1 ...
                            └─0.5s宽─┘ └──── 静默 1.6 s ────┘ └─0.5s宽─┘
```

**三条判据，都指向"只是打印抽稀"：**

1. **跳变规律**：每次都在 2 s 边界重复出现（1.5~1.8 s），
   **真实卡顿不会如此规律**。
2. **`loop_dt` 同期连续**：`loop_dt`（游戏时间增量）中位 0.10~0.20 s、
   max 0.30~0.40 s，**说明控制循环一直在跑、节奏正常**。
3. **只有"打印的 t"在跳，"循环的 dt"没跳**：若是真卡顿，两者会**同时**跳。

### 5.4 与 kOS 卡顿的区别（两个独立问题，别混淆）

用户提到的"kOS 写日志会短暂卡顿"是**另一个**问题，我也已处理：

| | kOS 写日志卡顿 | kRPC 控制台跳 2 秒 |
|---|---|---|
| 原因 | 主循环里**每 0.05~0.1 s 拼一个 57 字段的字符串**（30+ 行 `round()` + 字符串拼接）——kOS 的字符串运算很慢 | **打印抽稀是取模**，窗口 0.5 s / 周期 2 s |
| 证据 | 段内 `log_dt=0.1`，近地 `+0.05`（最高 20 Hz） | 跳变严格落在 2 s 边界 |
| 影响 | 真的拖慢 kOS 脚本帧 | **只影响控制台观感，不影响控制** |
| 处理 | **已注释掉**（§1 第 4、5 处） | 未改（见下） |

**⇒ 两个问题都定位清楚了。**

> 补充：kRPC 侧**历史上**确实有过真实卡顿（`150743` dt_max=**2.48 s**、
> `154838` 1.51 s），那是 `draw()` 每帧约 80 次 RPC 写造成的（上一轮已定位）。
> **但本次四趟的 dt_max 只有 0.32~0.38 s，与"跳 2 秒"无关。**

### 5.5 关于这个打印本身（是否需要改？）

**我没有改它**（用户只要求解释）。若将来想让它更连续，两种改法：
- 改为"每 0.5 s 打一次"：`if tt - _last_print > 0.5:`（需加状态变量）
- 或把模数改小：`int(tt*2) % 2 == 0` ⇒ 窗口 0.5 s、周期 1 s（跳变降到约 0.5 s）

**但请注意**：`print` 本身也有成本（写终端）。本项目对帧时间敏感，
**抽稀反而是在保护控制循环**。若只是观感问题，建议**保持现状**。
