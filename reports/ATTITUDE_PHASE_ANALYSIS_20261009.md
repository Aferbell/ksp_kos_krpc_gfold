## 0. 三十秒结论

**姿态跟踪的定量事实**（215317，全程）：

| 量 | p50 | p90 | max |
|---|---|---|---|
| 真实矢量误差 `att_err` | **9.50°** | 19.26° | 28.80° |

| 方位角误差 `\|az_err\|` | 2.00° | 173.35° | 177.50° |

**三个定性结论**：

1. **姿态误差 = 推力方向误差，不是"姿态好不好看"的问题。**
   推力沿机身，故姿态误差直接等于轨迹误差。
   实测推力方向误差 `vec_err` p50 = **9.47°**，且
   **38% 的帧水平有效出力 < 0.5**、**21% 的帧水平推力方向反了**。

2. **姿态误差的 93% 来自"倾角没跟上"，不是"方位角没转过来"。**
   （精确球面分解，215317；但 164053 是 52/48，见 §3.3 —— **因趟而异**）

   水平有效出力只有 0.234。** 而此时正是最需要横向修正的时候
   （`vh` 从 26 降到 17），于是水平修正被白白浪费。

**根因（按证据强度）**：
- **权限足够，是控制策略问题**：相位 A 需 `alpha ≥ 18.1 deg/s²`，
  实有 28.0（p50）—— 但 2.78 s 只转到 20/35°（达成率 57%）。
- **轴间争夺**：偏航 `|po_z|` 是俯仰 `|po_x|` 的 **2.3~12.9 倍**；
  偏航饱和帧的倾角误差是未饱和帧的 **1.71 倍**（10 趟汇总，n=943）。

- **【新发现】控制循环卡顿**：帧间隔标称 0.16 s，实测最大 **2.48 s**；
  且 **`seg_draw`/`seg_auth`/`seg_rpc` 算了但从未落盘** —— 无法定位。
- **【新发现】`check_py.ps1` 静默漏报 pyright**：恰好 1 个错误时正则不匹配

## 3. 姿态误差的量化归因

### 3.1 姿态误差 = 推力方向误差（这是唯一要紧的口径）

```
vec_err（机身 vs 指令的矢量夹角）：p50=9.47  p90=19.14  max=28.56 deg
水平有效比 horizEff：p50=0.643  p90=2.656
  horizEff < 0.5 的帧：38%      <- 有效出力不足一半
  horizEff < 0   的帧：21%      <- 水平推力方向【反了】
```

分段的"方向未对齐"时间：

| 段 | 总耗时 | 方向误差>15° 占比 |
|---|---|---|
| A | 3.09 s | **2.48 s (80%)** |
| B | 5.38 s | 0.00 s (0%) |
| C | 4.96 s | 1.82 s (37%) |
| D | 4.81 s | 1.32 s (28%) |
| E | 2.04 s | 0.00 s (0%) |

**段 A 是最浪费的**：80% 的时间推力方向偏 >15°，而此时正需要横向修正。

### 3.2 姿态误差浪费了多少横速修正能力

> **⚠️【2026-10-10 更正】本节的口径有缺陷，数字不可直接引用。**
>
> 本节把"实际水平推力"按 `r = -he/|he|`（指向瞄准点）分解为"有用/浪费"。
> **但这个口径在刹车阶段会系统性误判**：载具靠惯性冲过瞄准点后，
> 唯一正确的动作是**逆速度刹车**，而刹车方向**正好与 `-he` 相反**，
> 于是分解会把**正确的全力刹车记成 100% 浪费**。
>
> 这解释了为什么本节表格里 **A 段与 D 段的 `有用冲量` 是负数**
> （当时我已标注"为负"却未深究）—— 那不是"推力背离目标"，
> 而是"推力在正确刹车、被口径误判"。
>
> **独立验证**（`dot(hd, dve_dir)`，`hd` = 指令水平方向、
> `dve` = 速度误差方向）：在 215317 与 2026-10-10 的四趟日志上
> **p50 = +0.980~0.999**，即**指令方向几乎完全是逆速度阻尼**，
> 而非"朝瞄准点"。故 `-he` 口径不适用。
>
> **正确的口径**见 `dev/reports/HORIZONTAL_CONTROL_20261010.md` §2.3：
> 同时看 `aim = a·(-he)` 与 `brake = a·(-v)`，并用 `ang(hd, -v)` 判性质。
>
> **下面的原始数字保留供追溯，但"浪费 10%"这个结论【作废】。**

用几何分解（朝向瞄准点 = 有用，垂直/反向 = 浪费）：

| 段 | 有用冲量 | 浪费冲量 |
|---|---|---|
| A | −2.143 m/s | 0.230 m/s |
| B | +1.835 | 0.882 |
| C | +2.858 | 0.182 |
| D | **−5.907** | 0.821 |
| E | +3.713 | 0.199 |
| **合计** | **+0.357** | **2.315 m/s** |

全程浪费冲量 2.31 m/s，占"需消掉的横速"（23.16 m/s）的 **10%**。

**⇒ 姿态误差的直接代价是 10% 的横速修正能力**（不是全部，但也绝非可忽略）。
**注意段 A 和段 D 的"有用冲量"为负** —— 这两段推力净效果是**推离目标**。

### 3.3 误差分解：倾角 vs 方位角（精确球面）

## 4. 根因分析（我的假设与证伪）

### 4.1 ✅ 权限足够 —— 是控制策略问题（**已证**）

```
相位 A: 需转 D=35°, 窗口 T=2.78 s
        三角剖面所需 alpha = 4D/T² = 18.08 deg/s²
        实有 alpha p50 = 28.01, min = 5.59
        => 权限足够
        但实测 tilt_act 只到 20.0° (达成率 57%)
```

按 alpha 分组的跟踪差（**单调关系，强证据**）：
```
alpha  0- 8 deg/s² -> |dTilt| p50=17.55
alpha  8-14        -> |dTilt| p50=10.35
alpha 14-22        -> |dTilt| p50= 3.80
alpha 22-40        -> |dTilt| p50= 5.66
```
低权限确实跟踪更差 —— 但相位 A 权限是 **28**（高区间），跟踪差仍 **22.67**。
**⇒ 相位 A 的问题不是权限，是"权限没用在俯仰上"。**

### 4.2 ✅ 轴间争夺（**已证，且跨趟一致**）

**偏航长期吃掉大部分控制权限**（10 趟汇总）：

```
|po_z|(偏航) / |po_x|(俯仰) 之比（各趟中位）：
  150743=4.4  151358=4.4  154838=12.9  160001=3.4  213600=5.8
  214641=9.8  215317=6.0  164053=2.5   172711=2.3  175002=6.8
=> 稳定在 2.3 ~ 12.9 倍
```

**偏航饱和帧的倾角误差显著更大**（10 趟汇总，n=943）：
```
偏航饱和帧   n=111  |dTilt| p50=14.20  p90=28.32
偏航未饱和帧 n=832  |dTilt| p50= 8.30  p90=21.12
=> 比值 1.71 倍
```
（单看 215317 是 2.6 倍，但**跨趟汇总是 1.71 倍** —— 我最初用了单趟数值，
现按汇总修正。方向一致，幅度更小。）

**⇒ 偏航与俯仰确实在争夺权限，且偏航饱和时倾角跟踪明显变差。**
这与 §3.3 的"倾角主导"一致：**偏航抢了权限，所以倾角跟不上。**

### 4.3 ⚠️ 方位角 180° 反转的时间代价（**部分成立**）

```
T_rev = 2*sqrt(D/alpha)  （三角速度剖面反转 D 度所需时间）
14 趟中 6 趟 T_rev > T_left（落地前转不回来）：
  213600  T_rev=5.01s T_left=1.76s ratio=2.85  drift=+18.47
  151358  T_rev=4.86s T_left=1.99s ratio=2.44  drift= +2.91
  175002  T_rev=3.88s T_left=2.42s ratio=1.60  drift= +1.54
  ...
但 corr(drift, ratio) 仅 +0.230，corr(drift, D) = +0.420
```
**⇒ 有物理基础，但不能单独解释漂移幅度。**

## 5. 【新发现】控制循环卡顿 + 三个耗时段未落盘

### 5.1 卡顿是真实的，且不小

```
帧间隔标称 0.16 s（time.sleep(0.02) 后按游戏时间节流）
实测最大帧间隔：
  150743: 2.480 s
  154838: 1.511 s
  215317: 1.252 s
  213600: 1.154 s
  ...
14 趟中 11 趟有 >0.4 s 的卡顿
```
**卡顿期间执行器保持最后写入值** ⇒ 载具带着旧指令飞。

**已排除"游戏暂停"**：`wall/game` 比值 p50=1.012、max=1.776 —— 循环真的在实时跑。

**但卡顿不是漂移主因**（`corr(drift, stall_imp)=+0.018`）。
它的危害是**姿态控制更新率下降**：5.4 Hz 下再丢 1.25 s = 少 7~8 次纠正。

### 5.2 ⚠️ 三个耗时段算了但从未落盘（**可直接修**）

`run()` 里算了 5 个耗时段，**只落了 2 个**：

| 段 | 变量 | 是否落盘 |
|---|---|---|
| `seg_rpc` | 上一帧结束→本帧开始 | **❌ 未落盘** |
| `seg_auth` | 权限采样 | **❌ 未落盘** |
| `seg_state` | `state()` | ❌（`rpc_ms` 覆盖了它） |
| `seg_ctrl` | 控制律 | ✅ `ctrl_ms` |
| `seg_draw` | **`draw()` 画线** | **❌ 未落盘** |

**`draw()` 是最大嫌疑**：它每次更新 ~40 条线 × (`.start`+`.end`) = **~80 次 RPC 写**。

**耗时账（215317）**：
```
每帧 wall 间隔   : p50=190.0 ms  p90=264.0 ms  max=1210 ms
ctrl_ms (已落盘): p50= 36.5 ms  p90= 60.5 ms  max=  76.5 ms
rpc_ms           : p50=  5.8 ms  p90= 23.0 ms  max=  75.1 ms
未入账           : p50=147.7 ms  max=1058.4 ms   <- 就是没落盘的那三段
```

**⇒ 只要把 `seg_draw`/`seg_auth`/`seg_rpc` 落盘，就能立刻定位卡顿。**
`--no-debug-lines` 也可以直接做 A/B 对照。

## 5B. 【新发现】`check_py.ps1` 会**静默漏报** pyright 错误

### 5B.1 现象

HANDOFF §1 说 `check_py` 应为 **6/6 PASS**，实测输出是：

```
=== 0. pyright（Pylance 同源分析器）===
  (pyright 未安装，跳过)          <- 黄色，看起来无害
=== 1. pyflakes ===  PASS
...
*** 全部通过，可以上飞 ***
```

**但 pyright 其实装了**（`pyright 1.1.414`），并且**报了一个真错误**：

```
gfold_land.py:2780:26 - error: 类型为"None"的对象不可下标 (reportOptionalSubscript)
1 error, 0 warnings, 0 informations
```

### 5B.2 根因：正则只匹配复数 "errors"

`tools/check_py.ps1:62`：
```powershell
if ($prText -match '(\d+) errors') { ... } else {
    Write-Host '  (pyright 未安装，跳过)'    # <- 落进这一支
}
```
pyright 在**恰好 1 个错误**时输出单数 `1 error, 0 warnings`，
不匹配 `errors` ⇒ 落进 else ⇒ 打印"未安装，跳过"、**不计入 $fail**。

已实测验证：
```
"1 error, 0 warnings"  -match '(\d+) errors'  ->  NOT MATCHED   (漏报)
"0 errors, 0 warnings" -match '(\d+) errors'  ->  MATCHED n=0   (正常)
```
**⇒ 这是"恰好 1 个错误"才能触发的盲区**，2 个及以上会正常报 FAIL。

### 5B.3 被漏掉的这个错误是真问题（虽然当前不可达）

`gfold_land.py:2776-2780`（`fin_control` 内）：
```python
        else:
            target_direction = None            # <-- 2776
        # ---- 记录 ----
        self.tilt_cmd = math.degrees(math.acos(
            _clamp(float(target_direction[0]), 1.0, -1.0)))   # <-- 2780 下标 None
```
`target_direction = None` 只在 `FIN_TILT_HOLD` 为假时走到，
而当前 `FIN_TILT_HOLD = True`（常量）⇒ **运行时不可达，不会崩**。

**但两点值得注意**：
1. 这是另一会话 P3（FIN 段）引入的 —— `backups/30`（P3 前）pyright **0 错误**，
   当前 **1 错误**。已核实是我本窗口之前就存在的，不是本次分析引入。
2. 一旦有人把 `FIN_TILT_HOLD` 改成 `False`，**当场 `TypeError` 崩溃**
   （正是 §2 硬规矩里最忌讳的"跑到那一行才炸"）。

### 5B.4 建议修法（两处，都很小）

| # | 位置 | 改法 |
|---|---|---|
| **a** | `tools/check_py.ps1:62` | 正则改为 `'(\d+) errors?'`（`s?` 兼容单复数） |
| **b** | `gfold_land.py:2776` | `else` 分支改为 `target_direction = np.array([1.0,0.0,0.0])`（与 `_up` 同义），或把 2780 行移入 `if FIN_TILT_HOLD` 分支内 |

**(a) 影响所有后续检查的可信度** —— 在没有 (a) 之前，
"6/6 PASS"**不能证明** pyright 干净。
