## 2. 两个门的逐条比对（根因）

| 条件 | kOS `B1040-9.ks:1376` | kRPC `gfold_land.py:3593` | 是否一致 |
|---|---|---|---|
| 高度上限 | `h_aim < gfold_h(150)` ⇒ `alt < 517+150 = 667` | `alt < GATE_ALT(667)` | ✅ 一致 |
| 合速度 | `v_now:mag < gfold_vmax(120)` | `vmag < GATE_VMAX(120)` | ✅ 一致 |
| 在锥内 | `dist_hz <= h_gnd/tan(gfold_cone 48°)` | `cone_ok`（同式） | ✅ 一致 |
| **横速** | **`v_hz < vh_gate(10)`** | **（无此条件）** | ❌ **不一致 ← 根因** |
| 高度下限 | `h_gnd > p66_h(30)` ⇒ `alt > 47` | `alt > GATE_ALT_MIN(358)` | ⚠️ kRPC 更严（安全兜底，无害） |
**⇒ 两门只差一条**。kOS 要求横速先收干净（那是段1 的设计职责），
kRPC 却只要"高度够、速度够、在锥内"就放行并开始解算。
于是 kRPC 早 3~4.5 s 满足，而这段时间 kOS 仍握着 `lock throttle`。

### 2.1 【重要补充】用 kOS 侧日志交叉核对（`log-B1040-9/land_log_*.csv`）

kOS 侧日志含**门的原始变量**（`h_aim`/`vh_now`/`vh_gate`/`gfold_cone_ok`），
我起初据此得出一个**看似矛盾**的结论，必须澄清：

```
land_log_47928190（612 帧）
  首次满足 cone_ok    : row  72  alt=18541.3
  首次满足 vh<10      : row 387  alt= 2916.5   <- 很早！
  首次满足 |v|<120    : row 495  alt= 1077.4
  首次满足 h_aim<150  : row 542  alt=  662.4   <- 最后
  => 逐帧判断【整条门】从未同时为真
```

**看起来"vh 早就满足、h_aim 最后满足"，似乎该由 `h_aim` 决定交班 ——
但这与"重叠窗口由 vh 造成"矛盾。真相是：**

**`vh` 会回升。** 同一趟日志里：
```
alt=3177 m : vh=17.75
alt=2916 m : vh= 9.68   <- 首次 <10（但此时 h_aim=2404，远不满足）
...（中间 vh 回升）
alt= 660 m : vh=46.7    <- 又回到 47！
```
**⇒ `vh<10` 在 alt≈2900 只"短暂"满足过，那时 `h_aim` 还差得远；
等到 `h_aim<150`（alt≈662）时，`vh` 已经涨回 46~47。
所以 kOS 必须继续飞到 `vh` 再次收敛到 10。**

**由 `gfold_state.txt` 的实测 handoff 行确认**（这是 kOS 真正交班那一刻的抄录）：
```
GFOLD_HANDOFF ... alt=519   v=17.6 vz=-14.66 vh=9.99 mass=190.1
GFOLD_HANDOFF ... alt=576.4 v=20.3 vz=+17.74 vh=9.9  mass=182.5
```
**两行的 `vh` 都紧贴 9.9~9.99（= `vh_gate`）** ——
因为 kOS 门要求 `vh<10`，它能交班的那一瞬 `vh` 必然紧贴 10。

**而 kRPC 日志首帧是 `alt=648~654, vh=23.7~40.4`** ——
**更高、更快**。⇒ **kRPC 确实先满足、先解算**，重叠成立（用户观察正确）。
两种数据不矛盾，因为它们是**不同时刻**。

**另一个副产品结论（kOS 段1 的水平行为，值得单独注意）**：

`vh` 与 `dist_hz` 在段1 都是**非单调**的，且呈"先收干净再反弹"：

```
land_log_47928190:
   alt=2754 m : vh= 5.18   dist_hz=589
   alt=1100 m : vh=42.22   dist_hz=372
   alt= 733 m : vh=47.65   dist_hz=192
   alt= 638 m : vh=46.32   dist_hz=126     <- kRPC 门在此满足
   alt= 536 m : vh=33.39   dist_hz= 37
   alt= 519 m : vh= 9.99   dist_hz=  8     <- kOS 放权（handoff 行）
```
`dist_hz` 在 alt≈650 时还有 **93~131 m**，到放权时收到 **8~14 m**；
`vh` 同期从 **46~47** 收到 **9.9**。
**⇒ kOS 段1 确实在最后 130 m 里把横速与偏差都收干净了 —— 它做到了设计职责，
只是"做到"的时刻在 kRPC 门之后。** 这正是重叠窗口的由来。
（也说明方案B 让 kRPC 多等这 130 m 是**合理**的：那段时间 kOS 正在有效工作。）

### 2.2 【最干净的证据】"多等的高度"= 门高度 − 放权高度

`gfold_state.txt` 是 kOS 的 `LOG` **追加**文件，跨趟累积了 **112 条**
`GFOLD_HANDOFF` 行，因此可以**直接比较两个 `AIM_ALT` 时代**：

| 时代 | `GATE_ALT`（kRPC 门） | 实测 kOS 放权高度 | **差** | n | 放权时 `vh` |
|---|---|---|---|---|---|
| `AIM_ALT=1000` | 17+1000+150 = **1167 m** | p50 = **1165.7 m** | **−1.3 m** | 52 | 9.45 |
| `AIM_ALT=500`（当前） | 17+500+150 = **667 m** | p50 = **562.7 m** | **−104.3 m** | 35 | 9.90 |

**⇒ 这是最干净的因果证据**（两组 `n` 都足够大，且放权时 `vh` 几乎相同）：

- `AIM_ALT=1000` 时代：放权高度与门高度**几乎重合（差 1.3 m）** ⇒ **无重叠**。
  那时段1 有足够高度把 `vh` 提前收到 10 以下，kOS 与 kRPC 的门**同时**满足。
- `AIM_ALT=500` 时代：放权高度**比门低 104 m** ⇒ **重叠 104 m**。
  这正是"kRPC 门已满足、但 kOS 还要多飞 104 m 去收 `vh`"的直接量化。

**⇒ 完全印证 §2：把 `AIM_ALT` 降到 500 之后，两门的 `vh` 差异
才从"无害"变成"104 m 的重叠"。**
（与 `gfold_land.py:222-232` 里"这条风险未消除"的注释一致；
本次是**第一次把它定量测出来**。）

**方案B 的安全性由此确认**：放权高度 517~576 m（35 条 p50=562.7），
距 `GATE_ALT_MIN=358` 仍有 **159~218 m** 余量
⇒ **kRPC 不会因等 `vh<10` 而超时**。

> 另附：`gfold_state.txt` 里还有 25 条 `alt p50=5032.7, vh p50=219.2` 的行，
> 属于更早的 `AIM_ALT=3000` 时代（放权时 `vh` 高达 219）——
> 印证了 `B1040-9.ks` 里"`vh_gate` 从 35 收到 10"的历史动机。

**⚠️ 这一点代码里其实已经写过，只是被当成"未消除的风险"而非 bug**
（`gfold_land.py:222-232`）：

> `⚠️【必须知道并接受的风险（kOS 里记录的历史否决理由）】`
> `交班高度降到 667 m 后，到 kRPC 兜底门 GATE_ALT_MIN=358 只剩 309 m。`

## 3. 重叠窗口的定量（4 趟）

日志 `t=0` = kRPC 门满足那一刻。重叠窗口 = 到 `vh` 首次 <10。

> **时序精度说明**：严格说，kRPC 的门满足后先 `break`（`gfold_land.py:3619`）、
> 再起后台线程解算（`3680`）、然后才进主循环并在**每帧末尾**写日志。
> 故日志第一行比"门满足"晚约 1 帧（≈0.18 s），而解算（实测 `solve_ms`
> 148~209 ms）在这段时间内完成。**所以"日志 t=0"≈"解算完成"**，
> 与用户目视的"31 秒画线"一致（§5 的 offset 31.67 s）。
> 这使"重叠窗口"的估计**偏保守**（真实窗口可能再长 ~0.2 s），
> 不影响结论。

## 4. 【硬证据】窗口内确实是 kOS 在驱动油门

**判据**：若 kRPC 真正掌控，则
`thrust_n = thr_cmd × available_thrust × t_scale`，
故 `thr_real / thr_cmd` 应 **≈ `t_scale`**（约 1.5）。
若 kOS 的 `lock throttle` 仍生效，实际油门由 kOS 决定，
该比值会**大幅偏离**。

脚本：`dev/analysis/prove_kos_control_in_overlap.py`

| log | 重叠窗口内 `ratio/t_scale` | 释放后 | 判定 |
|---|---|---|---|
| 124409 | **4.29** | 0.95 | 窗口内被 kOS 覆盖 |
| 125000 | **3.55** | 0.79 | 窗口内被 kOS 覆盖 |
| 130003 | **5.08** | 1.00 | 窗口内被 kOS 覆盖 |
| 132420 | **4.62** | 1.00 | 窗口内被 kOS 覆盖 |

**逐帧样例（124409）**：
```
    t   thr_cmd  thr_real  t_scale   ratio  ratio/t_scale
 0.23     0.091     0.402    1.000    4.42   4.42   <-- 重叠窗口
 0.92     0.165     0.438    1.584    2.65   1.67
 1.49     0.071     0.481    1.584    6.79   4.29
 2.57     0.069     0.538    1.584    7.82   4.94
 ---  释放后 ---
 x.xx      ...       ...     1.584    ~1.5   0.95   <-- 回到 1.0
```
**⇒ 窗口内 kRPC 写 0.069 的油门，实际执行的是 0.538 等效油门（7.8 倍）。
kRPC 那时"以为"自己在控制，其实没有。** 这正是用户从油门指示看出的现象。

**独立交叉验证（用原始牛顿值，不依赖 thr_real）**：

`thrust_n` 是 `Vessel.thrust` 的实测求和（牛顿），与 `thr_real` 无关，
是第三条独立证据：

```
    t    thrust_n     thr_cmd   thr_real   推算油门
 0.21     4597880      0.106      0.541      0.511
```

**⇒ 三条独立证据一致**：窗口内 kRPC 指令 0.11，实际推力等效油门 0.63~0.70。
**kOS 在以约 5~6 倍于 kRPC 指令的油门飞行。**

## 7. 与"水平控制问题"的关系（诚实界定）

用户说"其他的就是之前一直探讨的水平控制问题"。本节的目的是**分清**两件事：

| 现象 | 是否由重叠窗口造成 |
|---|---|
| `plan_vz−vz` = −37 m/s（接管瞬间） | ✅ **是**（解算点≠接管点） |
| 接管瞬间 `trk_pos_h` 2.0~2.7 倍 | ✅ **是** |
| 重叠窗口内油门 3.5~5.1 倍不符 | ✅ **是** |
| 落点偏 0.43~12.21 m | ❓ **不是**（见下） |
| 水平"穿越-漂回"、方位角反转、yaw 抢权限 | ❌ **不是**（上一轮已独立定位，是水平律本身） |

**关键判据**：重叠窗口长度与落点距离呈**负**相关
（`corr(land_dist, rel_t) = −0.842`，`corr(land_dist, drop) = −0.767`）——
即**等得越久，落点反而越准**。若重叠窗口是落点误差主因，应为正相关。

**⇒ 结论：重叠窗口损害的是"交接瞬间的跟踪质量"和"控制权归属"，
但它【不是】落点误差的主因。落点误差仍归上轮定位的水平律问题。**
（n=4 很小，此结论的强度有限，但方向明确。）

**关联报告**：水平律本身的深入分析见
`dev/reports/HORIZONTAL_CONTROL_20261010.md`（同批四趟日志、独立分析，1152 行）。
该报告有 **三项修正/新发现**，其中第一项**也推翻了我上一份报告的一个结论**：

1. **口径修正（影响我的上一份报告）**：把水平推力按"指向瞄准点 `-he`"分解为
   有用/浪费，**在刹车阶段会系统性误判**（刹车方向正好与 `-he` 相反）。
   故 `ATTITUDE_PHASE_ANALYSIS_20261009.md` §3.2 的
   "姿态浪费 10% 横速修正能力" **已作废**（该节已加更正说明）。
   正确口径：同时看 `aim = a·(-he)` 与 `brake = a·(-v)`；
   实测 `dot(hd, dve_dir)` p50 = **+0.98~0.999** ⇒ 指令几乎完全是逆速度阻尼。
2. **★ 新发现：`ah_sat` 与 `tf_cap` 是同一条件**，不是两个独立证据。
   代码级确认（`gfold_land.py:1898-1905`）：
   `dbg_tf_cap = _tilt_allow`，而

## 8. 两个方案

### 方案A：kRPC → kOS 反向通信，令 kOS 提前放权

**用户原提议**："一旦出现 kRPC 门满足开始结算但 kOS 门没有满足的情况，
kRPC 向 kOS 发信息使其主动停止。"

**通信可行性（已核实）**：

- **kOS → kRPC 的消息机制对 kRPC 不可用**：kOS 的
  [`MESSAGE`/`CONNECTION`](https://ksp-kos.github.io/KOS_DOC/commands/communication.html)
  只在 **kOS↔kOS** 之间工作（processor/vessel 两种队列），
  kRPC **没有** kOS service（已核对本机 Python 客户端 0.6.0 的
  `krpc.services`：只有 SpaceCenter/Drawing/... 无 kOS）。
- **kRPC 也无法远程执行 kOS 代码**：没有该 RPC。
- ✅ **可行的通道 = 复用【已有的文件通道】**：
  kOS 的 Archive 卷就是磁盘目录
  `D:\...\Ships\Script`（`KOS_ARCHIVE_DIRS` 已如此配置），
  kOS 用 `LOG ... TO "0:/gfold_state.txt"` 写、kRPC 用普通文件读。
  **反向同理**：kRPC 写一个文件，kOS 用
  [`OPEN(...):READALL`](https://ksp-kos.github.io/KOS_DOC/structures/volumes_and_files/filecontent.html)
  读。已实测该目录可写可读。

**设计**：

```
① kRPC 门满足（现行条件）但 kOS 尚未放权时，
   kRPC 写 Ships/Script/gfold_stop.txt：
       GFOLD_STOP t=<game_ut> req=vh0
② kOS 主循环（B1040-9.ks:1282 `until FALSE {`）每帧（或每 N 帧）检查该文件：
       if exists("0:/gfold_stop.txt") {
           读第一行，若含 "GFOLD_STOP" 且时间戳在最近 2 s 内：
               立即执行【现有的放权序列】（ctrl_main=false / unlock ×2 /
               pilotmainthrottle=0），随后照常走 break 分支。
       }
③ kOS 放权后删掉该文件（DELETE），避免下一趟误触发。
```

**代价与风险**：
- ⚠️ **`LOCK` 语义风险**：kOS 的 `lock throttle` 在**物理帧**内持续生效。
  文件检查发生在**脚本帧**（`until FALSE` 每帧一次）。若脚本帧慢于物理帧，
  仍会有帧级滞后 —— 但比现在的 3~4.5 s 小 2~3 个数量级。
- ⚠️ **kOS 文件 IO 很慢**（`print`/`LOG` 几十 ms，读盘类似）。
  每帧读文件会给段1 循环增加可观的耗时。**建议每 5~10 帧查一次**。
- ⚠️ **需要在 kOS 侧新增 `OPEN/READALL/DELETE` 用法** ——
  而 `B1040-9.ks` 全文**从未用过**文件读 API（只有 `LOG ... TO` 写）。
  这是**新的代码路径**，需要单独验证（kOS 的 `OPEN` 失败会
  **抛异常并终止整个脚本** —— 与 `ship:id` 那个坑同类）。
- ⚠️ **kOS 单线程**：读盘期间不飞行。
- ⚠️ **kRPC 继承了 kOS 未收完的横速**：接管时 `vh` 23~40、
  `dist` 69~110（见 §8.2 表）。

### 方案B（用户新提议）：统一两个门的判据

**做法**：给 kRPC 门**补上 `vh < 10`**，与 kOS 门一致。

```python
# dev/krpc/gfold_land.py，GATE_* 常量区（约 L237 附近）新增：
GATE_VH_MAX = 10.0        # 必须与 boot/B1040-9.ks 的 vh_gate 一致

# run() 的门判据（约 L3593）改为：
if (alt < GATE_ALT and vmag < GATE_VMAX and cone_ok
        and alt > GATE_ALT_MIN and vh < GATE_VH_MAX):
```

**为什么这样改就够了**：kRPC 在门处**只做"等待"**，
一旦条件满足就 `break` 出等待循环并**立即开始解算**
（`gfold_land.py:3619` 的 `break` → `3627` 起解算）。
所以只要让 kRPC 的条件**不早于** kOS 的条件满足，
kRPC 就不会在 kOS 还没放权时抢跑。

**收益**：
- ✅ 消除重叠窗口（3.0~4.5 s / 119~138 m）；
- ✅ 消除规划过期（解算点 = 接管点 ⇒ §6 的 2.0~2.7 倍扰动归零）；
- ✅ kRPC 接管时 `vh<10`、`dist` 6~14（kOS 段1 已把活干完）；
- ✅ **无新增通信机制**、无新 IO、无 `OPEN` 异常风险；
- ✅ 改动量：**2 处**（1 个常量 + 1 个条件）；
- ✅ 可离线回归（`check_py` / `check_cols` / 门判据单测）。

**代价与风险**：
- ⚠️ **接管高度从 648 m 降到 ~519~576 m**（实测 `gfold_state.txt` 的四条 handoff 行：
  alt = 517.2 / 550.6 / 519.0 / 576.4）。
  `alt − GATE_ALT_MIN` 从 **290.9 m → 159~218 m**。
  但此时 `vh<10`，消横速所需高度也小得多。
- ✅ **kOS 一定能在 `GATE_ALT_MIN=358` 之上满足 `vh<10`**：
  四趟实测 handoff alt = 517~576，**余量 159~218 m**。
  （判据来自 `gfold_state.txt`，是 kOS 真正交班那一刻的抄录，最可靠。）
- ⚠️ **`vh` 在段1 非单调**（§2.1）：alt≈2900 时曾 <10，alt≈660 时回到 46~47。
  因此**不能用"曾经 vh<10"判定**，必须要求**当前帧**同时满足全部条件 ——
  方案的实现天然满足这一点（逐帧判断），但**排查时容易误判**，
  需在报告/注释里写清。
- ⚠️ **若某趟 kOS 段1 收不干净横速，kRPC 会一直等到 `alt<358` 才放行**，
  那时 kRPC 门仍可用（`alt>GATE_ALT_MIN`），但余量更小。
  **建议加一条"兜底"**：`vh<GATE_VH_MAX` **或** `alt < GATE_ALT_MIN + 60`
  （即"横速没收干净但快到底了，也必须接手"），避免死等。
  ⚠️ 注意兜底会重新引入"kRPC 先于 kOS 满足"的可能（若在 `alt<418` 时
  kOS 仍未放权）—— 所以兜底应同时**接受**"kOS 可能仍握着油门"这一事实，
  并由方案A（若实施）或 `verify_takeover_step` 的 `thr_real` 判据来暴露。

**推荐：方案B 为主，方案A 作为备选/可选加固。**
