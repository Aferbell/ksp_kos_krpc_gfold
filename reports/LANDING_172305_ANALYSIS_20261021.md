## 2. 竖直通道：跟踪精度很好，但有 99.7 m 的「面积欠账」

| 阶段 | `vz` 误差 p50 | `vz` 误差 max | 高度误差 p50 | 高度误差 max |
|---|---|---|---|---|
| 早期 0~3 s | **−15.18** | −23.36 | −0.11 | +19.90 |
| 中段 3~15 s | −0.65 | −22.13 | −0.01 | +1.37 |
| 末段 15~18 s | **−0.05** | −0.13 | −0.06 | −0.09 |
| FIN 前 18 s+ | −1.08 | +6.06 | −0.04 | +1.36 |

```
∫(vz − plan_vz)dt = −99.7 m      （负 = 实际比规划多掉了这么多米）
```

**读法**：

- **高度跟踪好到离谱**：中段 `plan_alt − alt` 的 p50 只有 **−0.01 m**（1 厘米）。
- 但 `vz` 早期差 −23 m/s：**开局就比规划掉得快**。这来自 `est_time=0.5s` 的状态外推
  与首帧 `alt` 已经比 `plan_alt` 低 19.9 m（见 §5 的未定项）。
- 控制器一直在补这 99.7 m 的欠账：**判据是高度误差始终 ≈0，说明它确实在追**。
- 代价是：为了「不落后于高度」，竖直通道一直贴着 `av_need` 上界跑，
  没有留出真正的减速余量。**这正是 §3 出事的前提。**

## 3. 末段为什么会爬升（核心）

### 3.1 数据

```
t      alt      vz       av_plan  av_need   need−plan   av_up   被削?
19.84  27.98   −13.26   18.14    17.64     −0.50      17.64
20.07  25.29   −11.49   17.49    17.53     +0.04      17.53
20.28  23.29    −7.84   19.57    14.38     −5.18      14.38   削
20.50  22.63    −0.06   25.30     9.45    −15.84       9.45   削
20.75  23.44    +5.38   25.30     3.93    −21.36       6.86   削
```

`av_plan > av_need` 的帧：**13/15 = 87%**（t>17.5 段）。

### 3.2 机理（四步，每步有数字）

```
① av_need = g0 + (vz² − tgt²) / (2h)          tgt = AVER_TGT_VZ = 2.0

② 刹停瞬间 vz 从 −7.84 变 −0.06，分子 (vz² − tgt²) 由 +57.5 变 −4.0
   => need 从 17.53 骤降到 9.45（一帧内掉 8.1）

③ a_up 被 need 上界削到 9.45，但油门指令还没退（上一帧 0.53，本帧 0.29）
   => 推力撤不及时

④ 载具继续上升 => vz 转正 +5.38 => 超过 CLIMB_ABORT_VZ=5.0 => 程序退出
```

### 3.3 为什么设计时没想到

`av_need` 的推导前提是「**载具一直在下降**」。当 `vz` 穿过 0 时：

```
vz = −7.84  =>  (vz² − 2²) = +57.5  =>  need = 9.81 + 57.5/(2h)  很大
vz = −0.06  =>  (vz² − 2²) = −4.0   =>  need = 9.81 − 4.0/(2h)   变小
vz = +5.38  =>  (vz² − 2²) = +25.0  =>  need 又变大，但此时已爬升
```

**上界在 `vz≈0` 附近有个「谷」**：`need` 先变小（允许推力撤），
等 `vz` 真的转正后又变大（想压回来）—— 但那时动能已经攒进去了。

`AVER_TGT_VZ=2.0` 意味着「目标触地垂速 2 m/s」，所以 `vz` 本不该穿 0。
穿 0 说明**前一段刹过头了**：从 −15.05 到 −0.06 只用了 0.89 s，
平均减速 16.8 m/s² —— 而 `av_up` 给的是 17.7（净 +7.9）。

**根因不是「刹过头」，是「刹早了」**：`av_need` 全程贴着上界跑（见 §2），
到 `alt≈25 m` 时 `vz` 还有 −11.5，而规划只要求 −8.0。**多出来的 3.5 m/s 必须在这 8 m 里消掉**，
于是控制器只能全推，一帧的 `loop_dt=0.22 s` 就改 3.6 m/s —— 精度不够，必然过冲。

## 4. `FIN_DESCENT_VZ` 2.0 → 1.0：改了，但要说明它治不了这个病

### 4.1 它只在哪生效

```
starship_land.fin_control():1708     _vz_tgt = −abs(FIN_DESCENT_VZ)
调用条件 starship_land:2653          alt <= TARGET_ALT + FIN_ALT = 17 + 1 = 18 m
```

**本趟最低 `alt=22.63 m`，从未进入 FIN 段** ⇒ 改它对这一趟完全无效。

### 4.2 那为什么还要改

口径统一。当前三个「目标垂速」互不一致：

| 常量 | 值 | 用在哪 |
|---|---|---|
| `AVER_TGT_VZ` | 2.0 | `av_need` 上界（gfold 全段）|
| `TERM_DESCENT_VZ` | 2.0 | **死常量**，代码无任何引用 |
| `FIN_DESCENT_VZ` | **1.0（本次）** | FIN 段目标垂速 |

改完之后：**gfold 段允许收到 −2，FIN 段再收到 −1**。
这是「两级收敛」，比原来（都是 −2，FIN 段没有进一步减速价值）更合理。

### 4.3 如果要让**整体**触地速度降到 1.0

必须改 `AVER_TGT_VZ`（2.0 → 1.0），不是 `FIN_DESCENT_VZ`。
本次按用户要求「其他不变」，**没有动它**。

### 4.4 顺带发现的死常量

`TERM_DESCENT_VZ`（=2.0）**全项目零引用**：只在 `starship_config:241` 定义、
`starship_land:100` 导入、以及一句注释里出现。末段下降律实际用的是
`AVER_TGT_VZ`（通过 `av_need`）。**本次不动它**，只在报告里记录，
避免「改一个常量」变成「改三处口径」。

## 5. ⚠️ 一个必须标注的未定事项

用相邻帧算真实竖直加速度，与推力能给出的对比：

```
t      loop_dt   dvz/dt     推力净加速度   满推理论上限   判定
19.84  0.220     +8.13      +8.07         23.36
20.07  0.220     +8.04      +7.98         23.40
20.28  0.200    +18.25      +7.81         23.44
20.50  0.200    +38.92      +4.61         23.48    **超物理上限**
20.75  0.240    +22.63      −0.33         23.53
```

**`t=20.50` 的 `dvz/dt = +38.92 m/s²`，而满推理论上限只有 23.48 m/s²。
这在物理上不可能只由推力产生。**

三个可能原因，本脚本无法区分：

| 可能 | 说明 | 怎么验证 |
|---|---|---|
| (a) 已触地 | 载具在 t≈20.4 已碰到地形，地面反作用力把 vz 顶成正的 | 加 `situation` 列 |
| (b) 时标不符 | 全段 `sum(loop_dt)=17.44 s`，墙钟 20.55 s，**少 15%**；末段尤甚 | 同帧记录 `sc.ut` |
| (c) 速度采样异常 | 参考系/采样问题 | 用位置差分交叉验证 |

注意 `alt=22.63 m` 时 `TARGET_ALT=17 m`，**离触点还有 5.6 m**，
所以 (a) 需要「地形比 TARGET_ALT 高 5 m」才成立 —— 这个假设本身也待验证。

**下一次实飞必须做的事**：

1. 日志加一列 `situation`（`landed` / `splashed` / `flying`）；
2. `climb abort` 触发时同时打印 `alt` / `vz` / `situation` / `sc.ut`；
3. 用「位置差分」而不是「速度差分」算竖直加速度，作为交叉验证。

**在拿到这些数据之前，本报告不把「爬升」的最终物理归因写成定论。**
