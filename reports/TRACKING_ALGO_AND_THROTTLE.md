## 第一部分：跟踪算法到底怎么控制的

### 0. 数据结构

求解器给出 4 个东西：

| 量 | 形状 | 含义 |
|---|---|---|
| `x` | (6, N) | 计划状态：`x[0:3]`=位置(目标系，x=天顶)，`x[3:6]`=速度 |
| `u` | (3, N) | 计划的**推力加速度**向量 `T/m`（不是油门！） |
| `tf` | 标量 | 计划总时长 |
| `N` | 标量 | 节点数（本项目 80） |

`dt = tf/N`，节点 `n` 对应时刻 `n·dt`。

### 1. 每帧七步（`track()`，`gfold_land.py:1153-1413`）

**第 1 步：找准「我在计划的第几个节点」**

```python
n_i = max(n_i - game_dt*0.2*N/tf,  find_nearest_index(x, error, vel))
n_i = max(0.0, n_i)
```

- `find_nearest_index`：遍历全部 N 个节点，找**三维位置距离最近**的那个，再在它附近用速度方向做**小数插值**（结果可能落在 `nearest_i ± 0.5`）
- `n_i - game_dt*0.2*N/tf`：本项目自己加的「索引不能倒退太快」限制
- 所以 `n_i` 是**小数**，比如 3.65 表示"在节点 3 和 4 之间偏 65%"

**第 2 步：在 `n_i` 处插值取出计划状态**

```python
x_i, v_i, u_i = sample_index(x, u, n_i, tf, N)          # 当前点
_x_i_, v_i_, u_i_ = sample_index(x, u, n_i + step, ...)  # 前瞻点
step = min(1.5*N/tf, |vel|/50*N/tf)
```

`sample_index` 用线性插值 `lerp(x[:,i], x[:,i+1], frac)`。
两个边界怪癖（照抄原仓库）：`index >= N-1` 返回全零；`index < 0` 时 `u` 取 `u[:,1]`。

**第 3 步：算指令 —— 这是算法的核心**

```python
target_a  = u_i  + (v_i  - vel)*K_VEL + (x_i - error)*K_POS    # 驱动【油门】
target_a_ = u_i_ + (v_i_ - vel)*K_VEL + (x_i - error)*K_POS    # 驱动【姿态】
```

- `K_VEL = 0.8`（速度项）、`K_POS = 0.5`（位置项），来自原仓库 `params.txt`
- **前馈项**：`u_i` —— 计划在这一点要求的推力加速度
- **反馈项**：速度误差 + 位置误差，比例修正
- `error` = 载具在目标系的位置，`vel` = 载具速度

**注意两行都用 `x_i`（当前点），不是 `x_i_`** —— 这是原仓库的设计，前瞻只体现在 `u_i_`/`v_i_`。

**第 4 步：锥限幅（`conic_clamp`）**

把 `target_a` 和 `target_a_` 各自压进「推力锥」内：

```python
a_ver_min = sqrt(min_mag² - a_hor²)  或  cos(tilt)*min_mag
a_ver_max = sqrt(max_mag² - a_hor²)  或  cos(tilt)*max_mag
a_ver = clamp(a_ver, a_ver_max, a_ver_min)   # 竖直被【抬到】正的下限
a_hor = min(a_hor, a_ver*tan(tilt))          # 水平削到锥面
```

- `min_mag = 0.05 * a_cap`，`max_mag = 1.00 * a_cap`（对应 `throttle_limit_ctrl = [0.05, 1.0]`）
- `tilt` = `min(max(tilt_traj + 8°, 25°), 89°)`，其中 `tilt_traj` 是**计划自己在当前节点的倾角**
  ⇒ 锥角跟随计划，不是固定 25°

**第 5 步：分派 —— 油门与姿态用不同向量**

```python
throttle         = |target_a| / a_cap        # 油门用【当前点】向量
target_direction = target_a_ / |target_a_|   # 姿态用【前瞻点】向量
```

**第 6 步：姿态 PID**

```python
target_direction_local = 地面系目标方向 变换到机体系
control_pitch = -clamp(pid_pitch.update(angle_around_axis(tgt_local, [0,1,0], [1,0,0]), dt), 1, -1)
control_yaw   = -clamp(pid_yaw.update(  angle_around_axis(tgt_local, [0,1,0], [0,0,1]), dt), 1, -1)
control_roll  =  clamp(avel_local[1] * 2.0, 1, -1)
vessel.control.pitch/yaw/roll = ...
```

- `angle_around_axis` 算的是「目标方向」相对机体参考轴、绕指定轴的角度 = **姿态误差**
- `kp=5, kd=2.5`（来自 `params.txt`）
- roll 直接消除角速度（无 PID）

**第 7 步：写执行器**

```python
vessel.control.throttle = throttle
vessel.control.pitch/yaw/roll = ...
```

### 2. 一句话总结这个控制律的性格

> **它是一条「按计划走」的前馈轨迹，加一圈比例反馈做修正。**

- 前馈 `u_i` 决定了**油门的主要大小**
- 反馈项 `(v_i-vel)*0.8 + (x_i-error)*0.5` 只做**修正**
- 姿态由 `target_a_` 决定 ⇒ **推力指向哪，取决于前瞻点**
- **如果姿态跟不上，油门再对也没用** —— 推力会指向错误的方向

## 第二部分：最新日志为什么油门一直很小

### 1. 现象

`thr_cmd` 分布（149 帧）：

| 值 | 帧数 |
|---|---|
| **0.05** | **117** |
| 0.22 ~ 0.33 | 4 |
| 0.65 ~ 0.83 | 22 |
| 0.95 ~ 1.00 | 6 |

`a_cmd_mag` 在这 117 帧里**恰好等于 `min_mag = 0.05·a_cap ≈ 2.65`**。

### 2. 直接机制：指令的**幅值**被压到下限

| frame | `a_cmd_up` | `a_cmd_h` | `\|a_cmd\|` |
|---|---|---|---|
| 4 | 0.046 | 2.648 | 2.648 |
| 20 | 0.173 | 2.660 | 2.665 |
| 50 | 2.434 | 1.135 | 2.686 |
| 100 | 2.460 | 1.147 | 2.714 |
| 120 | 2.595 | 1.210 | 2.863 |

`hypot(a_up, a_h)` 恒等于 `a_cmd_mag`（校验通过），而 `a_cmd_mag` 被钉在 `min_mag` 上。

**关键**：注意 `a_h` 和 `a_up` 在**此消彼长**，但幅值几乎不变 —— 这是 `conic_clamp` 的**幅值下限**在起作用：

```python
mag2 = hypot(a_ver, a_hor)
if mag2 < min_mag:
    k = min_mag / mag2          # 等比放大，直到幅值 = min_mag
    a_ver, a_hor = a_ver*k, a_hor*k
```

⇒ **原始指令的幅值远小于 `min_mag`，被机械地放大了。**

而 `throttle = |a_cmd| / a_cap = min_mag / a_cap = 0.05` —— **这就是 0.05 的唯一来源**。

### 3. 为什么原始指令幅值这么小？—— 根因是**姿态完全没跟上**

#### 3.1 姿态误差从头到尾都很大

| t | `tilt_cmd`（油门向量倾角） | `tilt_dir_cmd`（姿态目标） | `tilt_act`（真实姿态） | `att_err` |
|---|---|---|---|---|
| 0.77 | 73.01 | 78.35 | 20.78 | **57.35** |
| 0.96 | 87.98 | 89.00 | 18.79 | **70.21** |
| 1.14 | 89.00 | 89.00 | 18.05 | **70.95** |
| 2.59 | 89.00 | 89.00 | 33.53 | 59.68 |
| 27.44 | 25.00 | 25.00 | 66.10 | **79.07** |

- 计划要求 **89°（几乎水平）** 的大倾角制动
- 载具实际只有 **18~20°**（近乎竖直）
- **姿态误差 57~71° 一直存在，全程没有收敛**

#### 3.2 后果：推力方向错 ⇒ 水平无法制动

计划与实际的速度对比：

| frame | `plan_vh` | 实际 `vh` | 差 |
|---|---|---|---|
| 0 | 40.02 | 44.90 | −4.88 |
| 20 | 9.54 | 31.82 | **−22.28** |
| 60 | 0.00 | 17.84 | **−17.84** |
| 120 | 0.00 | 15.80 | **−15.80** |

计划要在 20 帧内把横速消到 9.5 m/s，实际只降到 31.8 —— **因为推力是竖直的，不是水平的**。

#### 3.3 新列 `trk_pos_h` 给出了铁证

| frame | `trk_pos_up`（竖直跟踪误差） | `trk_pos_h`（水平跟踪误差） |
|---|---|---|
| 20 | −5.64 | **64.34** |
| 60 | −0.01 | **207.18** |
| 120 | +0.01 | **380.63** |

> **竖直方向跟踪得几乎完美（误差 < 6 m），水平方向偏离到 380 m。**

这**决定性地**证明了：不是"油门算错了"，而是**推力全用在了竖直方向**（因为姿态是竖直的），水平方向完全没有制动。

#### 3.4 为什么竖直反而"完美"

因为载具竖直 → 推力竖直 → 竖直减速效率最高 → `vz` 恰好跟上了计划的下降率。
**这是一个"歪打正着"的巧合**，不是跟踪成功。

### 4. 为什么 `vterm` 让指令变小

| frame | `plan_vz` | 实际 `vz` | `vterm = (plan−actual)*0.8` |
|---|---|---|---|
| 4 | −80.63 | −67.98 | **−10.12** |
| 20 | −102.12 | −83.04 | **−15.27** |
| 60 | −139.71 | −127.48 | **−9.79** |
| 120 | −180.68 | −169.03 | **−9.32** |

载具比计划**下降得慢**（因为竖直推力过大），于是 `vterm` 长期为负 ≈ −10 ~ −15，
它把 `target_a` 的**竖直分量往下压**：

```
target_a[0] = u_i[0] + vterm[0] + pterm[0]
            ≈ 5.6   + (−15)     + (小量)     ≈ −9
```

⇒ `a_ver < 0` ⇒ `conic_clamp` 把它抬到 `a_ver_min`
⇒ 抬完之后 `a_hor = min(a_hor, a_ver·tan(89°))` 也被压得很小
⇒ 幅值不足 `min_mag` ⇒ **等比放大到 min_mag**
⇒ `throttle = 0.05`

**所以 0.05 不是"算出来的油门"，而是"算出来的指令无效、被下限兜底"的产物。**

### 5. 完整因果链（一句话版）

```
交接时载具姿态 ~20-24°，计划立刻要求 89°
   ↓ 姿态权限 α≈13.5°/s²，转 70° 需 ~4.5 s，来不及
姿态全程滞后 57-79°
   ↓ 推力方向几乎竖直
水平制动失效（vh 降不下来，trk_pos_h → 380 m）
   ↓ 但竖直减速反而过度
载具比计划下降慢 → vterm ≈ −10~−15
   ↓ 把 target_a 的竖直分量压成负数
conic_clamp 抬到 a_ver_min，幅值仍不足
   ↓ 触发幅值下限，等比放大到 min_mag = 0.05·a_cap
throttle 恒等于 0.05
```

**油门小是【结果】，不是【原因】。** 真正的问题在最上游：**姿态跟不上计划。**

## 第三部分：为什么姿态跟不上（本次未改，供你判断）

三种可能，本次日志**尚不能完全区分**（需要进一步验证）：

| 可能 | 支持证据 | 反对证据 |
|---|---|---|
| **A. 计划首帧倾角要求过高** | 交接时 `tilt_act≈20°`，计划 `tilt_cmd=89°` | 已修过一次（节点0改竖直），但本日志 `a_cmd_up=15.24, a_cmd_h=0` 帧 0-1 说明**节点 0 仍是竖直的** —— 修复**生效了** |
| **B. 姿态权限不足** | 实测倾角变化率仅 ~20-30°/s；转 70° 需 3-4 s | 但 `tilt_act` 从 18° 涨到 93°（f30），说明**有权限**，只是慢 |
| **C. 控制律增益/轴映射问题** | `att_err` 全程不收敛（57→71→79） | 代码与 `params.txt` 逐行一致 |

**注意一个重要的新观察**：帧 0-1 是 `a_cmd_up=15.24, a_cmd_h=0`（**纯竖直**），
说明**节点 0 竖直的修复已经生效**。但帧 2 起计划就切到 73-89°，姿态来不及。

**所以问题变成了**：计划从"节点 0 竖直"到"节点 1 起 89°"的**过渡太快**，
而载具需要 3-4 s 才能转过去。
