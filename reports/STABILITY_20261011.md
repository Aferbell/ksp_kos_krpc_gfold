## 2. 两种机制确实在叠加（这是本轮的核心价值）

| 杠杆 | 机制 | 单独效果 | 组合后 |
|---|---|---|---|
| **`KD` 4→6** | **加阻尼**（D 项更强，抑制振荡） | E: +0.122 → **−0.251** | 叠加 |
| **`T` 6→8** | **降需求**（外环带宽降、指令更缓） | E: +0.122 → **−0.157** | 叠加 |
| **两者** | 阻尼 + 降需求 | — | E: **−0.34 ~ −0.45** |

**⇒ 组合的 E 斜率（−0.34~−0.45）比任一单项（−0.16/−0.25）都更负，
说明两个机制**不是重复而是互补** —— 一个让回路更"黏"，一个让指令更"缓"。**

**旁证**：组合的 `ah_sat` 全部 **0%**（单改 0~2%、基线 7%）
⇒ 水平需求再也没超出能力，这正是"降需求"的预期效果。

## 4. ★ T5（偏距 248 m）为什么落点差 75 m —— 不是算法不稳

### 4.1 先排除"算法不稳"

- **T5 的 E 斜率 = −0.296（收敛）、包络比 0.15（误差在缩小）** ⇒ 回路稳定
- `dist` 从 248 m **一路降到 3.59 m**（t=12.72）⇒ **它真的飞到了目标**

### 4.2 真求解器确认**入场可行**

```
T5 入场: alt=647.6 dist=247.6 vz=-65.57 vh=6.22 mass=154.9t
  真求解器 -> optimal  tf=12.75  落地质量=145.0t      ✅ 可行
T4 入场: alt=655.1 dist=85.9  -> optimal tf=12.25     ✅
T3 入场: alt=629.5 dist=12.3  -> optimal tf=10.25     ✅
T2 入场: alt=652.1 dist=45.8  -> optimal tf=12.50     ✅
```

> **⚠️ 我在这个脚本上连犯两个错，已修正**（记录以免后人重犯）：
> ① `solve_p3p4_state(x0, mass)` 的 `x0` 是**6 维**（位置+速度），
>    我第一次传了 `(x0, v0, mass)` → TypeError；
> ② **kRPC 日志的 `mass` 列单位是 kg**（154857 kg = 154.9 t），
>    与 **kOS 日志（吨）不同**。我第一次乘了 1000 → 全部 infeasible（假结论）。
>    **两者修好后才是上面的 4/4 optimal。**

### 4.3 真正的失败机制：**终端收倾角把水平权限压死**

T5 的关键时刻（`t=12.72`，`dist` 最小 3.59 m）：
```
  当时 vh = 16.87 m/s   alt = 41.2 m
  a_up = 18.58, tilt_cmd = 6.29 deg (tf_cap 也是 6.29)
  => a_h_max = a_up*tan(tilt_allow) = 18.58 * tan(6.29deg) = 2.05 m/s^2
```

**为什么 `tilt_allow` 只有 6.29°？** 源码的终端收倾角逻辑（L1813-1838）：
```python
TILT_CAP_SLOPE = 3.0     # _tcap = clamp(alt/3, 5, 35)
TILT_TERM_ALT  = 90.0    # alt < 90 m 开始线性收倾角
TILT_CAP_LO    = 5.0     # 硬下限（仅在横速已消时允许收到这里）
_taper = alt / 90
if _vhoriz <= 1.0:  _tilt_allow = _tcap * _taper            # 横速已消 -> 收干净
else:               _tilt_allow = max(_tcap*_taper, min(_tcap, 5.0))
```

**⚠️ 我最初把原因归给"5° 硬下限"，核对源码后发现是 `taper` 在绑定**：
```
  alt    _tcap   _taper   cap*taper   谁在绑定
  90.0   30.00   1.000     30.00     taper
  50.0   16.67   0.556      9.26     taper
  41.2   13.73   0.458      6.29     taper   <- T5 的位置
  36.0   12.00   0.400      4.80     FLOOR(5) <- 只有 alt<36.7 才是 floor
```
**⇒ `alt=41.2` 时是 `_tcap*_taper = 13.73×0.458 = 6.29°` 在限制，
不是 5° 下限（`max` 只是没起到作用）。** 下限只在 **`alt < 36.7 m`** 才接管。

**⇒ 后果（算术很清楚）**：
```
消掉 vh = 16.87 m/s，在 a_h = 2.05 m/s² 下：
   需要时间 = 16.87 / 2.05  =  8.2 s
   需要距离 = 16.87²/(2×2.05) = 69.4 m
而 t=12.72 之后【只剩 1.47 s 飞行时间】
⇒ 物理上【来不及】。这不是稳定性问题，是【时间/权限不足】。
```
（若用 t=13.30 的 `a_h_max=1.68` 算，需要 **71.5 m / 10.2 s**，更不可能。）

**⇒ T5 的 `dist` 因此反向增大（3.59 → 25.32 m），末端带着 14.5 m/s 横速落地。**

> **注**：`tilt_act=12.07°` 比 `tilt_cmd=6.29°` 大得多（滞后），
> 所以**实际**水平推力对应 `18.58×tan(12.07°)=3.97 m/s²` ——
> 比命令的 2.05 大。但**方向**是错的（姿态滞后），
> 所以它并没有用来"刹车"，而是把载具继续推向一边（见上轮 224111 分析）。
> **这也是"姿态滞后在此处帮倒忙"的又一例证。**

### 4.4 T4 与 T5 的区别（为什么 T4 好得多）

```
T4: dist0= 85.9 m, vh0=0.85  <- 几乎零横速，只需"平移过去"
T5: dist0=247.6 m, vh0=6.22  <- 大偏距 + 有横速，且末端要先"停住"
```
**T4 的 `ah_sat` 仅 12%、`dist` 单调收 86→1.0 m；T5 是 88%。**

**⇒ 真正决定成败的不是"偏距大小"，而是"末端还有多少横速要消"。**
T5 的问题在于它**花了太多时间在横向移动上，导致末端没有足够时间减速**。

## 6. 诚实声明

1. **"周期不变性"这个结论在本轮【作废】**（§3）：新配置收敛太快，
   瓣数只剩 2~3，"周期"由 1~2 个间隔定出，不可信。
   我**不该**把这种数当周期用 —— 这是我的指标误用。
2. **T5 的 75 m 落点差不是算法缺陷**，而是"大偏距 + 末端横速来不及消"的
   **能力/时间**问题（§4）。**不要把它当成"算法不稳"的证据。**
3. **我在可行性检验脚本上犯了两个错并已修正**：求解器参数个数、以及
   **kRPC 日志 mass 单位是 kg（kOS 日志是吨）**。修正前得到"4/4 infeasible"
   的假结论。**这类单位/签名错误极易造成反向结论，特此记录。**
4. **样本量小**：正常入场的组合只有 **3 趟**，异常入场 **2 趟**。
   "5/5 收敛"是可信的方向性结论，但**具体改善幅度（3~6 倍）有不确定性**。
5. **`ah_sat=88%`（T5）与 `12%`（T4）的差异，我归因于"末端横速 + 终端收倾角"**，
   依据是逐帧时间序列与算术（§4.3），**但没有做闭环仿真复现**。
   **另外我把绑定约束从"5° 下限"更正为"`alt/90` taper"**
   （核对源码后确认：`alt=41.2` 时 floor 并未绑定，只有 `alt<36.7 m` 才是 floor）——
   这是我在同一段里犯的第二个错，已修正。
6. **三趟录屏我本轮只做了时间配对**，未逐帧目视复核姿态/SAS
   （上轮已确认过该机制）。
