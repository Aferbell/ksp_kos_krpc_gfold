## 二、根因（两个，按重要性排序）

### 根因 1（决定性）：交接瞬间姿态与计划要求差 48°

**实飞数据**（log 帧 0，t=0.18 s）：

| 量 | 值 |
|---|---|
| `tilt_dir_cmd`（姿态目标） | **72.53°** |
| `tilt_act`（真实姿态） | **24.52°** |
| `att_err` | **47.95°** |

**载具以 24.5° 的近乎竖直姿态进入 kRPC 交接，而计划立即要求 72–85°。**

**这为什么是致命的** —— 由实测的倾角变化率反推姿态权限：
```
帧 1.04→1.84（0.8 s）：tilt_act 21.75 → 4.96 deg
  => 约 -22 deg/s
```
按陀螺力矩估算（9×SSME、`gimbalRange=10.5°`、力臂 1.79 m、`I≈m·L²/12`）：
`α ≈ 13.5 °/s²`，转 60° 需 **约 4.2 s**（bang-bang）。

而计划的形状是（`dev/krpc/diag_plan_shape.py` 实测输出）：

| node | t | throttle | 说明 |
|---|---|---|---|
| 0–3 | 0.0–0.9 s | **0.80** | 立即 85° 大倾角水平制动 |
| 4 | 1.2 s | 0.22 | |
| 5–61 | 1.5–18.8 s | **0.10** | 低推力滑行，vz 从 −88 掉到 −183 |
| 62–78 | 18.8–23.6 s | 0.48→0.90 | 末端大推力刹车 |

**计划只给约 1.2 s 去完成一个需要 4.2 s 的姿态机动。**
姿态跟不上 ⇒ 推力方向错 ⇒ 前 3 帧把 0.86–0.95 的油门几乎全用在**竖直减速**上：

```
帧 0→3：vz  -82.98 → -85.37 → -79.21 → -69.65
        实测竖直净加速度 +12 ~ +17 m/s²（猛减速）
        计划只要求 u_ver≈3.8~5.4（净 -6 ~ -4.9）
```

⇒ 载具比计划**慢 20+ m/s** ⇒ `vterm[0] = (v_i−vel)[0]·0.8 ≈ −14 ~ −19`
⇒ 原始 `a_ver` 为负（−2.4 ~ −334 随发散加剧）⇒ 进入根因 2。

### 根因 2（把"跟不上"变成"完全不跟踪"）：`conic_clamp` 移植走样

**原仓库**（`demo3_gfold.py:292-314`）：
```python
if a_hor < min_mag*sin(t): a_ver_min = sqrt(min_mag**2 - a_hor**2)
else:                      a_ver_min = cos(t)*min_mag
if a_hor < max_mag*sin(t): a_ver_max = sqrt(max_mag**2 - a_hor**2)
else:                      a_ver_max = cos(t)*max_mag
a_ver = clamp(a_ver, a_ver_max, a_ver_min)     # <== 抬到 a_ver_min (>0)
a_hor = min(a_hor, a_ver*tan(t))
```
**竖直分量被抬到正的下限**，因此 `a_ver*tan(t)` 恒为正，**水平指令永不被清零**。

**我此前的实现**：
```python
if a_ver < 0: a_ver = 0          # 归零，而原仓库是"抬高"
cap_hor = a_ver*tan(t)           # a_ver=0 => cap_hor=0
if a_hor > cap_hor: a_hor = cap_hor   # 水平被清零
... 幅值不足 min_mag 时等比放大 ...
=> 返回 [min_mag, 0, 0]
```
**归零导致水平权限全失** —— 正是日志 `a_cmd_up=2.64, a_cmd_h=0.00, thr_cmd=0.05`
（112/148 帧，76%）的签名。

用实飞数值直接对比（`dev/krpc/diag_clamp_reference_vs_ours.py`）：

| 输入 | 倾角 | 原仓库 | 我的旧实现 | 丢失水平 |
|---|---|---|---|---|
| `a_ver=-2.44, a_hor=45` | 25° | `[2.484, 1.158]` | `[2.741, 0.000]` | 1.158 |
| 同上 | 85° | `[0.239, 2.731]` | `[2.741, 0.000]` | **2.731** |
| 同上 | 89° | `[0.048, 2.741]` | `[2.741, 0.000]` | **2.741** |
| `a_ver=+0.50` | 25° | `[2.484, 1.158]` | `[2.484, 1.158]` | 0（一致） |

**已修正**（`gfold_land.py` 的 `conic_clamp` 恢复原仓库语义）。
`dev/krpc/verify_conic_clamp_fix.py` 在整个输入网格（9×4×4=144 组）上
与逐行移植的原仓库实现**逐点一致**，且回归用例保留水平权限。

## 三、必须诚实说明：根因 2 的修正**不足以**解决问题

修正后再仿真（载具比计划慢 20 m/s 的情形）：

```
  t     plan_vz  veh_vz   raw_aver  a_ver  a_hor   thr
 0.00   -82.98  -82.98      3.79   3.785 42.680  0.782
 0.90   -86.31  -84.98     -6.86   0.048  2.741  0.050   <-- 仍降到 0.05
 1.80   -92.23  -86.98    -39.46   0.573  2.681  0.050
 3.60  -108.21  -90.98   -109.83   1.001  2.552  0.050
 7.20  -136.03  -98.98   -285.35   2.484  1.158  0.050
```

**`a_hor` 保住了（1.2–2.7 而非 0），但 `thr` 仍是 0.05。**
原因：原仓库在 `a_ver` 极端为负时，会把它**压到 `a_ver_min`（很小）**，
于是 `|a|` 落回 `min_mag`，**原仓库在这里同样会输出 0.05**。

⇒ **油门小不是跟踪 bug，而是"计划与载具已经发散"的必然结果。**
一旦载具比计划慢几十 m/s，任何限幅都只能给出很小的指令。
**根因 1（姿态跟不上）才是上游。**

## 四、修复方案

### 4.1 已做（照抄原仓库）
`conic_clamp` 恢复原仓库语义 —— 恢复水平权限，消除"纯竖直"退化。

### 4.2 待做（解决根因 1）—— 需要你选

**方案 A：降低交接点的姿态要求（推荐）**
交接时计划立即要求 85° 倾角，是因为**交接点速度仍大**（`vz=-88, vh=51`）。
若把瞄准点的交接门**上移**，让段 1 把速度收得更干净，则计划首帧倾角自然变小，
姿态来得及跟上。

- 现状：`GATE_AIM_H = 150`（瞄准点上方 150 m），交接时 `|v|≈102`
- 备选：把段 1 的目标改为"到位且速度≈0"，`GATE_VMAX` 从 120 收到 **40~50**
- **代价**：段 1 要飞更久、耗更多燃料；收益是消除 48° 姿态鸿沟

**方案 B：把姿态能力写进求解器约束**
在求解器里加一条 **倾角变化率约束**（`|tilt[n+1] − tilt[n]| <= ω_max·dt`），
逼计划自己产生"姿态来得及"的轨迹。G-FOLD 论文的标准做法。
- **代价**：必须**重新生成 codegen `.pyd`**（约束编译时固化）；可能使某些工况 infeasible

**方案 C：交接前由 kOS 预置姿态**
让 kOS 段 1 结束前先把载具倾到接近计划首帧的角度。
- **代价**：kOS 得知道 kRPC 的计划首帧角度，两边要耦合 —— **违反当前干净的分工**

**我的建议：先做 A。** 它最直接地攻击根因（姿态鸿沟），无需改求解器，
且与"交接点在瞄准点"的既有设计一致 —— 本来就该在速度收干净后交接。
