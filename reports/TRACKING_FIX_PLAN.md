## 2. 根因：求解器给了一条「先加速、再反向」的轨迹

### 2.1 直接证据

用交班点真实状态求解 P4（`alt=4994 / vz=−287 / vh=221`），看 `u[1]`（水平推力）：

| 节点 | 0 | 1 | 2 | 3 | 4 | **5** | **6** | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| `u[1]` | +38.90 | +38.98 | +39.07 | +39.14 | +39.21 | **+31.77** | **−39.34** | −39.40 | −39.44 |
| `vy` | 221 | 231 | 242 | 252 | 263 | 272.5 | 271.5 | 261 | 250 |

`vy` 一直是**正的**（朝目标飞），而 `u[1]` 在节点 5→6 **从 +39 翻到 −39** ——
**推力方向瞬间翻转 156°**（用完整 3D 矢量算），而 KSP 里一级的姿态转动很慢。

### 2.2 为什么求解器会这么解

P4 的目标函数（**照抄参考仓库** `GFOLD_direct_exec.py` line 126-129）：

```python
expression = 0
for i in range(N):
    expression += norm(x[4:6, i]) * (i / N)      # ← 权重 (i/N)
expression *= straight_fac
expression += -z[0, N-1] * N                     # 最大化落地质量
```

**权重 `(i/N)` 在早期趋近 0、晚期趋近 1** —— 即只惩罚"末段的水平速度"，
早期"随便冲"不花钱。于是燃料最优解选择：

```
早期水平能量过剩  →  先朝目标加速冲过去  →  再反向制动回来
```

**为什么水平能量过剩**：垂直下降被下降率约束拖到 21 s，而水平只需 ~12 s 就能消完，
多出来的 ~9 s 让求解器"绕一圈"（水平机动与垂直同时进行，不额外耗燃料）。

### 2.3 为什么参考仓库没暴露

它的用例 `x0=[1400, 450, -330, -20, 40, 40]`：**水平 450 m、横速 40 m/s**。
本项目：**水平 1314 m、横速 221 m/s**（大 5.5 倍）。过冲幅度随入场横速放大。

## 4. 方案

### 4.1 改动一：P4 目标函数权重 `(i/N)` → **常数 1**

**位置**：`dev/gfold/solver/gfold_p3p4.py`，P4 分支（约 line 196-201）

```python
# 原（参考仓库）
for i in range(N):
    expr += cp.norm(x[4:6, i]) * (i / N)

# 改
for i in range(N):
    expr += cp.norm(x[4:6, i])          # 常权重：全程同等惩罚水平速度
```

**实测效果**（同样用日志真实状态求解）：

| 场景 | 最大 \|Δu_hor\|（原 → 改） | 推力方向跳变（原 → 改） |
|---|---|---|
| alt 1500 / vh 90 | 65.35 → **26.14** | — |
| alt 2500 / vh 120 | — → **29.28** | — |
| alt 4994 / vh 221 | 71.12 → **25.77** | **156° → 31°** |

**关键改善**：`u_hor` 从"前 7 个节点 +39 加速"变成**一开始就是 −34.9（立刻制动）**：

```
原：  +38.9 +38.9 +38.9 +38.9 +38.9 +38.9 +39.1 | −26.2 −39.1 −39.1 …
      └────────── 与 vy 同向，加速 ──────────┘   └── 反向制动 ──┘
改：  −34.9 −34.9 −34.7 −34.6 −34.3 −34.2 −34.0 | −7.8 −4.2 −4.2 …
      └────────── 全程单向制动，机头基本不动 ──────┘
```

需要机头瞬间转动的角度：**156° → 31°**。

### 4.2 改动二：交班门降低（按你的选择）

**位置**：`boot/B1040-9.ks`（两个常数，**只改数值**）

| 变量 | 现值 | 改为 | 理由 |
|---|---|---|---|
| `gfold_h` | 5000 m | **1500 m** | 交班高度降到 1.5 km |
| `gfold_vmax` | 480 m/s | **180 m/s** | 配合低空交班 |

**kRPC 侧同步**（`dev/krpc/gfold_land.py`，两侧必须一致）：

| 常量 | 现值 | 改为 |
|---|---|---|
| `GATE_ALT` | 5000.0 | **1500.0** |
| `GATE_VMAX` | 480.0 | **180.0** |
| `GATE_ALT_MIN` | 358.0 | **不适用**（1.5 km 交班后不再需要下沿保护） |
| `START_ALTITUDE` | 5000.0 | **1500.0** |

**实测该交班点可解**：

```
alt=1500  vz=-95  vh=90   |v|=131   →  optimal, tf_m=15.2 s
```

> **注意**：`GATE_ALT_MIN=358` 是"可行域下沿"保护。交班高度降到 1500 后，
> 这个门会让 kRPC 在 358~1500 m 之间拒绝重解。需要把它降下来或去掉。

### 4.3 两处改动的关系

- **改动一（目标函数）是主因修复**：消除"先加速再反向"，让轨迹可跟踪
- **改动二（降交班）是辅助**：进一步减小过冲幅度、缩短求解时间

**建议先只做改动一，飞一趟验证。** 若仍不稳，再加改动二。
理由：改动一是根因，且只动一行；改动二涉及 kOS + kRPC 两侧 6 个常数，
还会带入 `GATE_ALT_MIN` 的连锁调整。

## 8. 改动三：首解等待期改为「沿速度反向减速」（2026-09-26）

### 8.1 用户要求

> "接管后计算好之前不应该不做任何事，应该瞄准速度反方向加油门继续减速，
> 但不能太大以至于反冲。"

### 8.2 旧实现的缺陷

旧 `hold` 是**纯竖直** + 只给「抵消重力 + 一半余量」：

```
实测（日志 183941）：thr=0.613 恒定
  竖直净减 20.3 m/s²（弱）
  水平减速  0        （完全不管 → vh 靠重力转向自然衰减，很慢）
```

交班时横速可达 221 m/s，不主动消掉等于把难题全留给 G-FOLD。

### 8.3 参考仓库本来就有这个模式

`demo3_gfold.py` line 428-435（`nav_mode == 'simple'`）：

```python
target_a = (-vel) * k_v*3 + (-error)*k_x*0 + v3(g0, 0, 0)
a_mag = npl.norm(target_a)
target_throttle = a_mag / (max_thrust / mass)
target_direction = target_a / a_mag
target_direction[0] = max(target_direction[0], min_tilt_cos)
target_direction[1:3] *= (1/norm(target_direction[1:3])) * sqrt(1-target_direction[0]**2)
```

即「**瞄准速度反方向 + 补重力 + 限制倾角**」—— 与用户要求完全一致。
本实现沿用该公式，另加**两道反冲保护**。

### 8.4 反冲保护（针对"不能太大以至于反冲"）

纯反推的竖直分量 = `|a|·|vz|/|v|`。当 `vz → 0` 时若仍满推，
净竖直可达 +39 m/s² ⇒ `vz` 由负变正 ⇒ **上冲**。两道限制：

| 限制 | 公式 | 作用 |
|---|---|---|
| ① 竖直分量上限 | `g0 + HOLD_UP_FRAC·(a_cap − g0)` | 不把竖直余量用满 |
| ② 与 \|vz\| 挂钩 | 净减速 ≤ `\|vz\| / HOLD_TAU` | 至少留 1 s 才消到 0，**vz 绝不穿越 0** |

两者取小 ⇒ `vz` 单调趋近 0 但永不反号。

### 8.5 `HOLD_UP_FRAC` 的取值（燃料权衡）

首解要 ~3.6 s，hold 期间烧的油**直接吃掉落地质量**（总预算约 42 t）：

| `HOLD_UP_FRAC` | 竖直净减 | 4 s 烧油 | 占燃料预算 |
|---|---|---|---|
| 0.75 | 29.5 m/s² | 9.5 t | 22%（太多） |
| 0.50 | 19.7 m/s² | 5.5 t | 13% |
| **0.40（选用）** | **~23 m/s²** | **~5.5 t** | **~13%** |

选 **0.4**：既明显强于旧版（旧版竖直净减 20、**水平为 0**），
又不至于把燃料烧在"等解算"上。

### 8.6 离线验证结果

| 场景 | 4 s 后 vz | 4 s 后 vh | 烧油 | 反冲 |
|---|---|---|---|---|
| 实飞交班 −301/217 | −236 | 147 | 7.2 t | **无** |
| 极端横速 −310/362 | −245 | 248 | 8.9 t | **无** |
| 边界 vz=−12（测保护） | **−0.3** | 0.0 | 8.0 t | **无**（渐近趋 0，不穿越） |

第三行专门验证反冲保护：`vz` 从 −12 渐近到 −0.3，竖直指令随之降到
~10 m/s²（仅补重力），**没有穿越 0**。

### 8.7 新增常量

`dev/krpc/gfold_land.py`：

```python
HOLD_UP_FRAC = 0.4    # 竖直推力分量上限 = g0 + 0.4·(a_cap - g0)
HOLD_TAU = 1.0        # 净竖直减速 <= |vz| / HOLD_TAU（防反冲）
```

## 10. 时序修正（2026-09-26，用户要求"解决之前说的时序问题"）

### 10.1 修正 A：`verify_takeover()` 不再阻塞（省 0.5 s 真空）

**旧行为**：同步 `verify_takeover()`，内部 `sleep(0.05)×10 = 0.5 s`，
且跑在**主循环之前** ⇒ `hold` 一帧都没写 ⇒ 这 0.5 s 火箭**无推力自由落体**。

**新行为**：拆成逐帧采样 `verify_takeover_step()`：
- 主循环第 1 帧就写执行器
- 每帧采一个 `(thr_cmd, thr_act)` 样本，跳过前 12 帧（写入生效期）
- 累计 `TAKEOVER_SAMPLES=40` 个有效样本后判定，不符比例 ≥60% 判失败
- **零额外耗时**，结论同样可靠

### 10.2 修正 B：轨迹起点对齐（误差 933 m → 2 m）

**旧行为**：首次解算传 `acc = np.zeros(3)` ⇒ 外推只有一阶项、速度完全不外推：
```
pos_est = error + vel*0.5        (直线外推)
vel_est = vel                     (速度不动)
```
而求解耗时 3.6 s 内火箭实际下降 1084 m，外推只覆盖 0.5 s×301 = 150 m
⇒ **轨迹起点比实际位置高 933 m** ⇒ P 项 `K_POS×933 ≈ 466 m/s²`（远超可用 49）

**新行为**：
- 新增 `hold_accel()`：预测 hold 段的**真实减速加速度**
- 新增 `_predict_est_time()`：外推时长 = **上次实测求解耗时 ×1.2**（夹在 0.5~6 s）
- 首次解算与周期性重解**都用**这套（重解本来就用实测差分加速度）

```
新: pos_est = error + vel*4.3 + 0.5*23.0*4.3²  →  下降 1086 m
    实际 3.6 s 内下降 1084 m                    →  偏差 2 m
```

### 10.3 修正 C：hold 期间可见 + `draw()` 不再静默失败

- `draw(self.plan)` 在 `plan is None` 时会 `TypeError`，被 `except` 吞掉
  ⇒ 表现是"完全看不到线且毫无提示"。现在显式判断 `plan is not None`
- 新增 `draw_target_marker()`：hold 期间在目标点画绿色竖线（建一次、只改端点）
  ⇒ 解算窗口内屏幕上不再是空的

### 10.4 修正 D：预热解算（用户提的"方向 1"）

> 用户："一级是时刻处于活动的"

**问题**：交班门一满足 kOS 立刻放权，而 kRPC 才刚开始首解 —— 那几秒火箭一直在掉。

**做法**：不等门满足就**提前起解**：
```
预热门（比交班门宽一档）: alt < GATE_ALT×1.25 且 |v| < GATE_VMAX×1.15
```
预解时按"继续下落到门"预测状态作为初值：
```
t_pred = (alt - GATE_ALT) / |vz|
pos_p  = 当前位置 - |vz|*t_pred
vz_p/vh_p ≈ 当前值（这期间发动机未开）
```
交接时若轨迹已就绪 ⇒ **零等待**直接进 gfold；未就绪则退回 hold 老流程（不重复起线程）。

**时间窗核算**：预热门到交班门高度差 1250 m，以 vz=300 计 = **4.17 s**
⇒ 即使 cvxpy 的 3.6 s 也够用；codegen 后 0.1 s 余量极大。

| 项 | 改动前 | 改动后 |
|---|---|---|
| 首解开始时刻 | 交班门满足时 | 门上方 25% 处 |
| 交接时轨迹状态 | 未就绪（等 3.6 s） | **已就绪（零等待）** |
| 等待期下坠 | 约 1100 m | **约 0 m** |

**新增常量**：`PREWARM_ALT_FACTOR=1.25`、`PREWARM_V_FACTOR=1.15`

**验证**：`dev/krpc/verify_prewarm.py`（预热门判据 5/5 通过；
预测状态精确落在 alt=5000；求解 0.087~0.109 s）
