## 0. 先纠正我上一轮的错误

我最初把 `restock-engine-375-corgi`（750 kN、万向节 4°）当成一级主引擎，**这是错的**。
按 craft 里的**部件位置**（VAB 坐标 y 从下往上）：

| 部件 | y | 数量 | 归属 |
|---|---|---|---|
| `SSME` | **1.79 m**（最底部） | **9 台** | **一级主引擎** |
| `restock-engine-375-corgi` | 37.34 m | 1 | 上面级 |
| `LiquidEngineRE-J10` | 48.45 m | 1 | 上面级 |

**验证**：9 × 1000 kN = 9.0 MN，日志 `max_thrust=8990529 N` ⇒ 吻合（差 0.1%）。

### 一级真实控制参数

| 项 | 值 | 来源 |
|---|---|---|
| 单台推力 | 1000 kN | `SSME.cfg:138` |
| 台数 | 9 | craft 位置统计 |
| **万向节** | **10.5°** | `SSME.cfg:184 gimbalRange` |
| 万向节响应 | 8 | `SSME.cfg:185` |
| RCS | `RCSblock.01.small` ×12，`thrusterPower=0.1`（最弱档） | `RCSblock_01_small.cfg:157` |

### 控制能力核算

```
m = 232.6 t, T = 8.99 MN, a_cap = 38.7 m/s², gimbal = 10.5°
万向节横向能力 = a_cap·sin(10.5°) = 7.05 m/s²   ← 只够微调
轨迹要求 u_hor ≈ 38 m/s²                        ← 需整机倾斜 75~80°
```

**关键认识**：横向机动**不靠万向节**，靠**整机倾斜**。
万向节的作用是产生**控制力矩**（转动整机）：

```
τ = 9 × F·sin(10.5°) × r ≈ 9 × 182 kN × 1.8 m ≈ 2952 kN·m
I ≈ m·L²/12 (L=30 m) = 1.74e7 kg·m²
α ≈ 9.7 °/s²  ⇒  转 75° 约需 2.8 s
```

**结论：姿态执行器（9×SSME，10.5°）不是瓶颈。**
用户"RCS 作用小、主要靠引擎矢量"的判断正确，但**问题不在执行器**。

## 2. 根因（已逐步复现到行）

### 2.1 `est_time` 被 0.5 s 下限抬高 ⇒ 轨迹起点超前 138 m

`_collect_resolve()` 采纳新轨迹时把 `gfold_n_i = -100`（"重新定位"）。
新轨迹用 `vessel_profile1()` 的**外推状态**作 `x0`，外推时长：

```python
est_time = _predict_est_time() = max(0.5, last * 1.2)
last = solve_ms/1000 = 0.149 s          # codegen 后实测
⇒ est_time = max(0.5, 0.179) = 0.5 s    # ← 被下限硬拉到 0.5
实际只用了 0.149 s
⇒ 外推【超前 0.35 s】
⇒ 轨迹起点比本机靠前 0.35 × 390 ≈ 126 m
```

> `0.5 s` 是**参考仓库为"执行延迟"设的常数**（它求解在后台跑，耗时不入外推），
> 本项目却用它代表"求解耗时"——两处**语义不同**，直接套用就成了误差源。

### 2.2 位置误差被 K_POS 放大成"向下推"指令

`dev/krpc/diag_clamp.py` 逐步打印（用真代码）：

```
x_i     = [3275.0, -261.0]        轨迹起点
err     = [3413.0, -351.0]        本机
x_i-err = [ -138.0,  +90.0]       本机【落后】于轨迹起点
v_i-vel = [    0.0,    0.0]       速度恰好相同
u_i     = [   3.41, -38.96]       轨迹起点几乎水平（85°）

u_i 贡献   = [   3.41, -38.96]
K_VEL 贡献 = [   0.00,   0.00]
K_POS 贡献 = [ -69.00, +45.00]    ← K_POS=0.5 × (-138)
------------------------------------------
target_a   = [ -65.59,  +6.04]    ← 【竖直分量变负！】
```

### 2.3 `conic_clamp` 为保物理性把竖直截零，**连带把水平一起清零**

```python
if a_hor < 1e-9: ...            # 不触发（a_hor=6.04）
hor_dir = a_hor_vec / a_hor
if a_ver < 0.0: a_ver = 0.0     # a_ver: -65.59 -> 0
cap_hor = a_ver * tan(89°) = 0 * 7.6 = 0     # ← 退化成 0
if a_hor > cap_hor: a_hor = cap_hor = 0      # ← 水平被清零
mag2 = 0 < min_mag(2.44)
if mag2 < 1e-9: return [min_mag, 0, 0]       # ← 纯竖直最小推力
```

**输出 `[2.44, 0.00, 0.00]`，与日志 `a_up=2.41~2.45 / a_h=0.00` 完全吻合。**

⇒ 水平指令被清零 ⇒ 姿态归零 ⇒ **不再跟踪轨迹**。

### 2.4 两个次要因素（会被放大，但不是根因）

| 项 | 说明 |
|---|---|
| `n_i` 允许负值 | `find_nearest_index` 给出 `fr=-0.5` ⇒ `n_i=-0.5` ⇒ 触发 `track()` 里 `if self.gfold_n_i < 0: target_a = [G0,0,0] + u_i` 覆盖分支（照抄参考仓库 line 391-392），与正常分支来回切换 |
| `n_i` 推进系数 0.2 | 参考仓库把**加号版**注释掉了（line 362），留减号版（line 363）。**实测两种符号差异很小**（`find_nearest_index` 主导），**不是根因**——我的这个假设已被实验否定 |

## 3. 修正（1 处，最小改动）

**`dev/krpc/gfold_land.py` → `_predict_est_time()`**：下限 `0.5` → `0.05`

```python
# 前
return float(min(6.0, max(0.5, last * 1.2)))
# 后
return float(min(6.0, max(0.05, last * 1.2)))
```

**为什么只改这一处**：根因是"外推超前"，而外推超前来自这个下限。
`conic_clamp` 与 `track()` 的分支**都是照抄参考仓库的正确逻辑**，
一旦 `est_time` 正确，`a_ver` 不会变负，那两个分支就不会被触发。

> 我一度改了 `conic_clamp`（用"虚拟竖直分量"避免清零），
> 但实测输出变成 `[0, 2.44] → tilt=90°`（纯水平姿态），**同样危险**。
> ⇒ 已**回退**，保持与参考仓库一致。
