## 1. P1：收紧内环 `j_max`（已实施）

### 1.1 依据（上一轮实测）

```
原判据 j_phys = a_up·sec²(θ)·sqrt(2·alpha·headroom)
  · 等效倾角速率上限 ≈ 39~44 deg/s
  · 而实际指令速率 p50 只有 3.7~10.6 deg/s
  ==> 余量 4~10 倍，限速器【从不生效】
     实测 j_used/j_max p50 = 0.20/0.26/0.135、ah_cap_bind = 0%
```

### 1.2 改动

```python
# 常量（新增）
JERK_SLEW_FRAC = 0.50      # 允许用掉物理 slew 的比例（1.0 = 原行为）

# 原代码
_j_max = max(JERK_GUARD_MIN, min(JERK_GUARD_MAX, _j_phys))
# 新代码
_j_lim = _j_phys * max(0.05, min(1.0, float(JERK_SLEW_FRAC)))
_j_max = max(JERK_GUARD_MIN, min(JERK_GUARD_MAX, _j_phys, _j_lim))
```

**为什么用"乘比例"而不是绝对 deg/s**：
物理上限正比 `sqrt(alpha)`，而 `alpha` 随油门变化 **8 倍**
⇒ 比例收紧能自动跟随权限，**低油门端不会过紧**。

### 2.3 我试过"正确的形式"（sin 加权），**仍然有害**

我推导了正确形式：方位角的三维代价是 `sin(tilt)·Δaz`，不是 `Δaz`，
故应限 `sin(tilt)·|Δaz|`。用真日志测（`test_p2_correct_form.py`）：

```
  FRAC=0.50:   限帧 4~23%，但"限时夹角"中位仍达 8~175°、
               横向损失达 6.6 m/s²
  FRAC=0.75:   限帧 0~18%，夹角中位 0.4~178°
  FRAC=1.00:   限帧 0~20%，夹角中位 100°、损失 0.54 m/s²
```

**⇒ 即使用 sin 加权，被限帧上仍出现 100~178° 的方向偏差**
（因为那些帧恰好是"穿越目标、方向本应翻转"的时刻）。
**⇒ 结论：方位角不该被限速，任何形式都会指错推力方向。**

## 5. `dev/.gitignore` 里写的是什么意思

> 说明：git 仓库根目录是 **`dev/`**（`git -C dev rev-parse --show-toplevel`
> = `…/Ships/Script/dev`），所以 `dev/.gitignore` 是这个仓库的**根忽略文件**。
> `dev/gfold/.gitignore` 是**上游仓库自带的**（见第 7 条），与本项目无关。

`.gitignore` 的作用：**告诉 git 哪些文件不要纳进版本库**。
本项目的规则按用途分 8 组，写法上有一个**很关键的特殊设计**：

### 5.1 常规组（1~7 条）

| 组 | 内容 | 为什么忽略 |
|---|---|---|
| ① Python 字节码 | `__pycache__/`、`*.py[cod]`、`*$py.class` | 每次运行自动重建 |
| ③ cvxpygen 生成物 | `cpg_p3/*`、`cpg_p4/*`、`solver/cpg_p*/`、`GFOLD_p3/`、`GFOLD_p4/` | 体积大、可由 `tools/gen_codegen.ps1` 再生 |
| ④ 编译产物 | `build/`、`dist/`、`*.so`、`*.dll`、`*.exe`、`*.pdb`、`*.lib`、`*.exp`、`*.obj`、`*.ilk` | 编译中间件 |
| ⑤ 虚拟环境 | `venv/`、`.venv/`、`env/`… | 本机相关 |
| ⑥ 编辑器/系统 | `.vscode/`、`.idea/`、`*.swp`、`*~`、`Thumbs.db`、`desktop.ini` | 个人配置 |
| ⑦ 类型检查缓存 | `.mypy_cache/`、`.pytest_cache/`、`.ruff_cache/`、`.coverage`、`htmlcov/` | 工具缓存 |
| ⑧ 外部参考仓库 | `gfold/` | 它是**独立 git 仓库**，纳入会被当成 embedded repo |
| ⑨ 恢复资料 | `recovery/` | 历史凭据，留本机不必进库 |

### 5.2 ★ 最关键的设计：**白名单式"例外放行"**（第 ② 组）

这是这个文件**最值得理解**的地方，也是它写了那么多注释的原因。

**问题**：`*.py[cod]` 这个模式会**连带匹配 `.pyd`**（Windows 的扩展模块），
而 `cpg_p3/cpg_module_p3*.pyd` 是**实飞必需件**。

**曾经的严重事故**（文件里 17-28 行记录的）：
```
cpg_p3/cpg_p4 被删掉后
  -> gfold_p3p4.py 的 _load_cgen() 找不到扩展
  -> 【静默回退】到 cvxpy
  -> 实飞 solve_ms 从 ~0.08 s 恶化到 3441 ms（约 48 倍）
  -> 载具在解算期间白掉 118 m 并整段失控
```

**⇒ 它不是"可有可无的优化"，而是实飞路径上的必需件。**
而"clone 出去没有它，程序能跑但慢 48 倍"这种失败**极难发现**。

**所以用了三段式规则**（先全忽略、再用 `!` 放行需要的）：
```gitignore
*.py[cod]                      # 先忽略所有字节码（含 .pyd）
!*.pyd                         # ① 兜底放行 .pyd（否则下面 ② 也救不回）
cpg_p3/*                       # ② 忽略整个生成目录
!cpg_p3/cpg_module_p3*.pyd     # ③ 但放行唯一的运行期必需件
```

**只有运行期真正需要的 `.pyd` 进版本库**；`build/`、`c/`、`cpp/`、
`problem.pickle`、`README.html` 等约 **37 MB** 中间产物仍被忽略
（它们可由 `tools/gen_codegen.ps1` 再生）。

**⑦ 那段"路径前缀"注释也很重要**（29-34 行）：
`.gitignore` 里的模式是**相对该文件所在目录**匹配的。
2026-09-28 求解器迁移后实际路径变成 `dev/solver/cpg_p3/*`，
而原来的 `cpg_p3/*` **只匹配 `dev/cpg_p3/*`** ⇒ 规则**静默失效**，
重新生成 codegen 时约 37 MB 中间产物会全变成"未跟踪文件"
（`git status` 里 16 条 `??`）。
**⇒ 修法是把两种路径都写上**（文件里就是这么做的）。

### 5.3 ⚠️ 我发现一个**真的 bug**（第 113 行）

文件**最后一行有问题**：
```
112: *.csv
113: *.log# ---- temp commit message file (not tracked) ----
114: _cm.txt
```

**`*.log` 与后面的注释被粘在同一行**，中间没有换行。
这导致：
1. `*.log` 这条**规则失效**（它被解析成 `*.log# ---- temp commit message file (not tracked) ----`，是个无意义模式）
2. 那条注释也失效
3. `_cm.txt`（第 114 行）**仍然有效**

**我用 `git check-ignore` 实测确认**（只读查询，未改动仓库）：
```
$ git -C dev check-ignore -v --no-index "test.log"
（空输出 ==> NOT ignored，规则确实失效）

$ git -C dev check-ignore -v --no-index "test.csv"
.gitignore:112:*.csv    test.csv        <== 对照组，工作正常
```

**影响**：`dev/` 下若有 `*.log` 文件（例如 `pip-log.txt` 之外的
`celerybeat-schedule` 之类，或 Python 脚本产生的 `.log`），
**不会被忽略**，会出现在 `git status` 里。

**修法**（一行，但我**没有动** —— 用户只要求解释）：
```gitignore
*.log

# ---- temp commit message file (not tracked) ----
_cm.txt
```
**⇒ 建议插一个换行。要我改的话说一声。**

## 6. 诚实声明

1. **P1 的"被限帧%"是【离线逐帧判据比较】，不是闭环仿真。**
   我**没有**做闭环复现，所以"被限 7~16%"只说明"判据会咬到这些帧"；
   实际飞行中被限后指令变化会反过来影响后续帧。
   **P1 的真实收益必须靠实飞确认。**
2. **我第一版 P1 的离线复算（`verify_p1_effect.py`）不可信，已作废**：
   它的 `FRAC=1.00` 对照组本应 ≈0，实测却是 −15~−22%。
