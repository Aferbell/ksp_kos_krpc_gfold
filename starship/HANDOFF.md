## 1. 【必须重算】惯量与姿态权限

**换载具时最容易搞错、后果最严重的一项。**
错误的值会让所有姿态增益、限速、规划锥角全部失效。

### 1.1 惯量

原值 `I_TRANSVERSE = 1.6e9` 是按均匀杆 `I = ML^2/12` 估算的，**偏大 3.9 倍**。
KSP 的部件质量集中在两端（油箱+引擎），实际转动惯量小得多。

**实测值**（3 份日志 428 样本，kRPC `Vessel.moment_of_inertia`）：

| 量 | 实测 | 配置 |
|---|---|---|
| `I_pitch = I_yaw` | 3.79e8 ~ 4.15e8 | **4.13e8** |
| `I_roll` | 8.42e6（只有俯仰的 2%） | 8.42e6 |
| `tau_pitch/yaw` | 1.35e8 ~ 1.42e8 N·m | **1.35e8** |
| `tau_roll` | 2.03e7 N·m | 2.03e7 |

**怎么重算**：飞一趟（哪怕失败），从日志读 `I_p`/`I_r`/`I_y`/`tau_p`/`tau_r`/`tau_y` 列的中位数。

### 1.2 alpha(throttle) —— 姿态角加速度随油门变化

万向节力矩 ∝ 推力 ∝ 油门，而 I 恒定 ⇒ **alpha 与油门线性相关**。

**实测拟合**（428 样本）：
```
alpha[deg/s^2] = 25.62 * throttle - 3.94
```

| 油门 | alpha | 场景 |
|---|---|---|
| 1.00 | 21.7 deg/s^2 | 满推 |
| **0.55** | **10.2 deg/s^2** | **悬停（本载具 TWR 1.82）** |
| 0.21 | 3.5 | 低油 |

对应 `starship_config.alpha_at_throttle(thr)`。

**为什么重要**：`TAU_SCHED_ALPHA_REF` 必须取**实测悬停值**，否则调度器失效：

| ALPHA_REF | 悬停 fac | 满油 fac | 结论 |
|---|---|---|---|
| 3.83（旧，错的） | 1.63→卡到 1.60 | 2.38→卡到 1.60 | **调度器恒定 1.60，等于没有** |
| **10.16（实测）** | **1.00** | **1.46** | 真正工作 |

### 1.3 姿态角速率物理上限

```
slew_max = sqrt(2 * alpha * headroom)      [rad/s]
```

物理意义：从静止加速到 slew、再同等减速停住，总角行程正好 = headroom（取 45 度）。

| 油门 | alpha | slew_max |
|---|---|---|
| 悬停 0.55 | 10.2 deg/s^2 | **30.2 deg/s** |
| 满推 1.00 | 21.7 deg/s^2 | **41.1 deg/s** |

对应 `starship_config.slew_max_deg(thr)`。

## 2. 【必须重算】求解器的规划锥角斜率

`starship_p3p4.PCS_SLEW_DEG_PER_NODE`

**这是 `deg/node` 不是 `deg/s`**，等效角速率 = `SLEW * (N-1) / tf`。

### 为什么必须按载具改

规划要求载具做不出来的动作时，控制器必然失控。实测事故：
```
tf=10.5 s 时 SLEW=8.0 的等效速率 = 8*79/10.5 = 60.2 deg/s
而 starship 物理上限只有 41.1 deg/s  ->  超限 47%
结果: tilt_cmd 出现 -88.7 deg/s 尖峰 -> 机身过冲 72 deg/s -> vh 从 3 反涨到 24
```

### 怎么算

```
SLEW_max(tf) = slew_max_deg(满油) * tf / (N4 - 1)
```

按**最坏 tf**（实测 replan 会压到 10.5 s）取值：

| tf | SLEW 上限 | |
|---|---|---|
| 10.5 | 5.46 | <- 最坏，取这个 |
| 13.3 | 6.91 | |
| 22.3 | 11.59 | |

**现取 4.0**（对 10.5 s 留 27% 余量）。

### 为什么不能动态算

`SLEW * tf` 是 **cvxpy Parameter 的乘积** ⇒ 非凸 ⇒ 破坏 DPP ⇒ cvxpygen 无法生成 C 代码。
（`starship_p3p4.py` 里「为什么不用 omega*tf」那段注释有完整说明。）

**折中方案的代价**：`tf=22.3`（典型首次解）时规划只用到 14.2 deg/s，即物理能力的 35%，
规划偏保守。但**保守 = 可跟踪**，这是正确取舍。

### 改完必须重新生成 codegen

```powershell
$env:PYTHONPATH="<root>\tools\stubs"
$env:PYTHONJULIAPKG_OFFLINE='yes'
python dev/starship/starship_codegen.py
```
**不重新生成 = 改动不生效**（SLEW 编译期固化在 .pyd 里）。

## 3. 【必须重算】推力口径与自校准

### 3.1 kRPC 的 available_thrust 不含 thrustPercentage 限幅

实测：
```
7 台 SSME @250%:  max_thrust*limiter 求和 = 16.49 MN
                  kRPC available_thrust   =  6.60 MN
                  比值 2.500  <- 恰好是 thrustPercentage 250%
```

**这是本工程最致命的历史 bug**：不校准会让 `a_net` 算成负数，直接放弃着陆。

### 3.2 标定公式

```
true_thrust = sum(Engine.max_thrust * Engine.thrust_limit)   # 只对活动引擎
ratio       = true_thrust / Vessel.available_thrust
```

`Ship.calibrate_thrust()` 实现。**采样窗口必须容纳这个比值**（现设 `[1.0, 4.0]`）。

### 3.3 换载具时的检查清单

- [ ] 引擎是否有 `KOSNameTag`（`e1`~`e33`）？改 `ENGINE_TAGS_KEEP`/`_OFF`
- [ ] 关引擎后的引擎数变化了？**必须重新标定**（`main()` 里已做）
- [ ] 跑一下 `dev/starship/api_check.py` 确认 kRPC API 存在

## 4. 【必须重算】交接门

### 4.1 门高度必须与 kOS 算式一致

```
kOS (superheavy.ks:1389): h_aim < gfold_h 且 v_now:mag < gfold_vmax
                          且 v_up < gfold_vz_max 且 gfold_cone_ok
h_aim = alt:radar - (target_alt + aim_alt)
       => 交班高度 = target_alt + aim_alt + gfold_h = 17 + 500 + 150 = 667 m
```

**kRPC 侧的 `GATE_ALT` 必须等于这个值**。历史上写成 `TARGET_ALT + AIM_ALT = 517`，
比交班点低 150 m，导致多滑行 150 m、vz 从 66.7 涨到 85.9、必然 infeasible。

### 4.2 门判据不能在 kOS 放行后挡路

**kOS 放行 = 控制权已在我们手上**。此时任何「等门」都是纯自由落体。

现在的设计：
- `wait_gate(handoff=...)` 非 None ⇒ **立即返回 True**
- 物理判据只做**能量预检告警**，不拦路
- 只硬性拒绝：① 游戏冻结（读数不可信）② `alt < GATE_ALT_MIN`（高度不足）

### 4.3 可解垂速上限随高度/横速变化

`starship_config.vz_gate_max(alt, vh)` —— 扫描表：

| alt | vz_max @vh=10 | @vh=40 | @vh=80 |
|---|---|---|---|
| 517 | 80 | 70 | 50 |
| 600 | 90 | 80 | 60 |
| 667 | 100 | 90 | 70 |

**为什么必须随高度变**：交班后无油门滑行，`vz` 只增不减。667 m / vz=66.7 滑到 517 m 就变成 86.0。

**换载具时**：用 `dev/starship/_scan_final.py` 重新扫一遍。

## 5. 【必须重算】控制器的跟踪律参数

### 5.1 前赡点 `TILT_LEAD_SEC`

机身姿态滞后 ≈ 与 `1/sqrt(alpha)` 成正比。
- 旧 B1040-9：`alpha≈0.35 rad/s^2`，实测滞后 1.2~2.2 s
- starship：`alpha≈0.178 rad/s^2`（悬停），sqrt(0.35/0.178)=1.40 ⇒ 滞后 ≈ 1.7~3.1 s

现取 **2.5 s**。

### 5.2 倾角上限 `TILT_CAP_LO/HI`

```
cap(alt) = clamp(alt / TILT_CAP_SLOPE, TILT_CAP_LO, TILT_CAP_HI)
```
- `TILT_CAP_HI = 35` —— **必须等于 `starship_p3p4.PCS_START_CAP_DEG`**（solver 有 assert 强校验）
- `TILT_CAP_LO = 3` —— 触地姿态要求

### 5.3 内环加加速度 `JERK_GUARD_MIN`

```
j_max = a_up * sec^2(theta) * sqrt(2*alpha*headroom)
```
按 `a_up≈8.1, sec^2≈1.5, alpha≈0.178 rad/s^2` ⇒ ≈ **3.9 m/s^3**（旧载具约 18.7）。
故 `JERK_GUARD_MIN = 0.8`（旧 2.0 已占物理上限一半）。

### 5.4 油门下限 `GFOLD_THROTTLE_MIN`

```
悬停油门 = g0 * m / T_max
```
- starship：9.81 * 987500 / 17.5e6 = 0.554（TWR 只有 1.82）
- 旧 B1040-9：0.171（TWR 5.8）

**TWR 越低，下限空间越小**。现取 `min(0.50, 0.96*悬停)`。

## 6. 【必须重算】阶段门槛链（2026-10-21-j 定稿）

> ⚠️ 本节是**换载具时第二容易搞错**的部分（第一是 §11 姿态 PID）。
> 核心认知：**`TARGET_ALT` 是「质心离地高度」，不是「腿离地高度」**。

### 6.1 四个高度必须严格递减，且互不重合

```
alt = TARGET_ALT + TERM_CLEARANCE   规划零速点 / 末段下降律接管
alt = TARGET_ALT + FIN_ALT          FIN 接管
alt = TARGET_ALT + LAND_ALT_EPS     非 FIN 路径判「已落地」
alt = TARGET_ALT                    规划归零点 = 着陆腿触点
```

**当前值（2026-10-21-h）：**

| 常量 | 值 | 推导出的门 |
|---|---|---|
| `TARGET_ALT` | **26.5** | 规划零点 26.5 m（见 6.2）|
| `TERM_CLEARANCE` | **20.0** | 末段律 46.5 m |
| `FIN_ALT` | **10.0** | FIN 接管 36.5 m |
| `LAND_ALT_EPS` | 1.0 | 触地判据 27.5 m |

**真实可用行程 = FIN 门 − 真触地读数 = 36.5 − 24.2 = 12.3 m**
（能兜住 22.5 m/s 的入口垂速，见 §6.4）

**改前的坑（都已实测验证）：**

```
改前:  22.0 / 18.0 / 18.0 / 17.0    <- LAND_ALT_EPS 与 FIN_ALT 的门【重合在 18.0】
       末段律窗口 4 m、FIN 窗口 1 m
       实测 4 m 窗口只有 1~2 帧，末段律来不及工作
```

### 6.2 【最容易搞错】`TARGET_ALT` 是「质心离地高度」，不是「腿离地高度」

**这是本项目最反直觉、代价最大的一条。**

```
┌────────────────────────────────────────────────────────────────────┐
│ TARGET_ALT 直接与 alt:radar / surface_altitude 比较，而这两个量     │
│ 都是「Measured from the center of mass」—— 从【质心】量，不是从腿。│
│ 所以 TARGET_ALT 的物理含义是「质心离地多高」。                      │
└────────────────────────────────────────────────────────────────────┘
```

**kOS 的 `alt:radar` 与 kRPC 的 `Flight.surface_altitude` 是同一个量**：
实测 10 趟交班点，两者只差 **p50=1.5 m / max=2.9 m**，换算成时间
0.020~0.040 s —— 正是「kOS 写文件 → kRPC 读到」的交班延迟。
**不存在「两个 API 读数不一样」的问题。**

**触地瞬间这个读数 = 质心到地面的距离，与载具长度成正比：**

| 载具 | 长度 | 真触地读数 | 程序里的 `TARGET_ALT` | 余量 |
|---|---|---|---|---|
| 旧 B1040-9 | 约 30 m | **14.63 m**（26 趟 p50）| 17.0 | **+2.37 m** ✔ |
| starship | 约 70 m | **24.20 m**（184650 实测）| **26.5** | **+2.30 m** ✔ |

**取 18.0 时的实测后果（`starship_log_20261021_184650`）：**

```
规划认为「质心降到 18 m」，而载具腿触地时质心还在 24.2 m
  => 规划要求【穿地 6.2 m】=> 永远到不了
  => alt=28 m 时 plan_vz=-2.34 而实际 vz=-16.76（差 14.4 m/s）
  => FIN 窗口 = (18+10) - 24.2 = 3.8 m < 一帧位移(3.9 m)
  => fin=0.00s，FIN 段一帧都没跑就退出
```

### 6.2.1 换载具时必须重测（不能抄）

```
1. 让载具落到地面（哪怕砸坏）
2. 读 flight().surface_altitude 的触地读数
3. TARGET_ALT = 触地读数 + 余量（旧程序口径 +2.4 m）
```

**不要照抄旧载具的 17，也不要凭「腿有多高」估。**
旧 17 与 starship 24.2 差 7 m —— 全部是几何差异。

### 6.2.2 必须与 kOS 侧同步

```
boot/superheavy.ks:209            local target_alt is 26.5.
dev/starship/starship_config.py   TARGET_ALT = 26.5
```

不一致时 `h_aim`/`h_gnd`（kOS）与 `error[0]`（kRPC）错位，交接门会提前/推迟放行。

**`GATE_ALT` 由 `TARGET_ALT + AIM_ALT + GATE_AIM_H` 自动推导，不要手改。**
当前 26.5 + 800 + 150 = **976.5 m**。

**验证脚本**：`dev/analysis/check_gate_sync.py`（自动解析两个文件并对比）。

### 6.3 `TERM_CLEARANCE` 同时是两个东西

```
# ① 求解器：规划零速点抬高
_x0_solver[0] -= TERM_CLEARANCE      # 少给求解器这些高度
r['x'][0,:]   += TERM_CLEARANCE      # 解完平移回来

# ② 控制器：末段下降律的触发门
_term_phase = (h_now < TERM_CLEARANCE)
```

**两者必须同高**，否则载具会在中间悬停（旧程序实测 211419 在 alt=21.8 m 悬停 27.1 s）。

### 6.4 `FIN_ALT` 受「刹车行程」硬限制

```
最大可兜入口 vz = sqrt(2 * a_net * H + FIN_DESCENT_VZ^2)
a_net  = a_cap - g = 30.42 - 9.81 = 20.61 m/s^2     （13 台回收构型）
H      = 【真实可用行程】= FIN门 - 真触地读数
       = (TARGET_ALT + FIN_ALT) - 24.2 = 36.5 - 24.2 = 12.3 m
```

| `FIN_ALT` | 名义值 | 真实行程 | 可兜入口 vz |
|---|---|---|---|
| 1.0 | 1.0 m | 1.0 m | 6.5 m/s ← 实测入口 6.7~93.7，完全兜不住 |
| **10.0（当前）** | 10.0 m | **12.3 m** | **22.5 m/s** |
| 15.0 | 15.0 m | 17.3 m | 26.7 m/s |

**换载具时必须重算**：`a_net` 和「真触地读数」都变了，同一个 `FIN_ALT`
能兜的速度也变。**注意用的是「真实行程」不是「名义 FIN_ALT」** ——
因为真触地读数比 `TARGET_ALT` 低（余量），真实行程总是比 `FIN_ALT` 大。

### 6.5 `AVER_TGT_VZ` 是三个「目标垂速」里唯一生效的

```
av_need = g0 + (vz^2 - AVER_TGT_VZ^2) / (2h)    <- 同时被末段律和 FIN 用
```

| 常量 | 是否生效 | 作用 |
|---|---|---|
| `AVER_TGT_VZ` | **生效** | 末段律 + FIN 的目标垂速 |
| `FIN_DESCENT_VZ` | **生效** | 仅 `fin_control()` 的 `_vz_tgt` |
| `TERM_DESCENT_VZ` | **零引用（死常量）** | 只在注释里出现，代码用 `AVER_TGT_VZ` |

> ⚠️ **`TERM_DESCENT_VZ` 的注释与代码不一致**：
> `starship_land:1441` 注释写「目标是 TERM_DESCENT_VZ」，但 1463 行实际用 `AVER_TGT_VZ`。
> 下次重构时应接入或删除。

### 6.6 FIN 触地保持段的其它参数

- `FIN_UP_MIN = 0.35`（悬停加速度的比例）—— 保证万向节有力矩
- `FIN_KD = 0` —— `a_need` 解析上已精确收到目标垂速，KD 越大越差（离线 5 工况验证）

**已知物理局限**：`thr=0` 时万向节无力矩，只剩反作用轮。本载具 `I=4.13e8`，
反作用轮提供的 alpha 极小（日志实测 `alpha_max=0.0~0.2 deg/s^2`），**姿态无法维持**。
这不是参数问题，是物理事实 —— 若要 FIN 段有姿态权限，必须**保持小油门**，不能清零。

## 8. 换载具的完整操作顺序

1. **改 `boot/superheavy.ks`**（或对应 kOS 脚本）的 `target_alt`/`aim_alt`/`gfold_h`/`gfold_vmax`/`gfold_vz_max`/`gfold_vdesc_k`
   —— `target_alt` 必须与 `starship_config.TARGET_ALT` **逐位一致**（见 §6.2）
2. **跑 `analyze_first_stage.py`** 拿干重/推力/几何
3. **改 `starship_config.py`**：质量、推力、引擎 tag、`TARGET_ALT`
4. **飞一趟**（哪怕失败），从日志**实测 `I_p`/`tau_p`/`alpha_max`**
5. **按实测改** `I_TRANSVERSE`/`GIMBAL_TORQUE`/`TAU_SCHED_ALPHA_REF`/`REF_SLEW_MAX`
6. **按实测 `err_x` 定 `CTRL_X_ROT_KP`**（§11.5.1：唯一约束是「P 项不饱和」）
7. **实测 `TARGET_ALT`（最容易搞错，必须先做）**（§6.2）：
   ```
   # 让载具落到地面（哪怕砸坏），读 situation==landed 那一刻的
   # flight().surface_altitude —— 它 = 质心到地面的距离
   TARGET_ALT = 触地读数 + 2.4      # 沿用旧程序的余量
   # 旧 B1040-9: 14.63 + 2.37 = 17.0
   # starship  : 24.20 + 2.30 = 26.5
   ```
   **不要照抄旧载具的值，也不要凭「腿有多高」估。**
   同步改 `boot/superheavy.ks` 的 `local target_alt is`。

## 11. 【必须重算】姿态环 PID —— 最容易搞错的一项

### 11.1 为什么 zeta 过阻尼还会过冲

`zeta` 公式假定 **D 项不饱和**。一旦 D 被 clamp，等效阻尼崩掉：

```
实测 t=13.61:  err=-0.0604 rad   omega=-0.264 rad/s   sched=1.60
  P = 19.2 * 0.0604 =  1.16
  D = 41.6 * 0.2640 = 10.98    <-- 是 P 的 9.5 倍
  输出 clamp 到 ±1.0  =>  D 被砍掉 91%
  => 实际是【饱和开关控制 bang-bang】，必然过冲
```

实测过冲：`tilt_act` 超过 `tilt_cmd` 5° 以上的帧 **30/61**，最大 **+92.5°**。

### 11.2 2026-10-21-d 定论：绝对角速度喂 D 项，本载具无解

**实飞 `starship_log_20261021_144058`（kd=2.0/kp=5.0，绝对角速度）**
> ⚠️ **本节的结论后来被 §11.5.1 部分推翻**：归一化只解决了 D 项，真正的瓶颈是
> **P 项饱和 3 倍**。保留此节是为了记住「只搬 kd、漏了 kp」这个错误。

| 观测量 | 实测 |
|---|---|
| `att_err` | 5° → **77.6°**，单调上涨，全程不收敛 |
| `tilt_cmd` vs `tilt_act` | 反复交叉 −6.7 / +21.9 / +31.2 / −15.7 / +49.6 / +34.8 |
| `avel_p` 峰值 | **0.96 rad/s (55 deg/s)**，超过物理 slew 上限 44.2 deg/s |
| `pid_sat_x` | t=4.4~19.5 几乎全程 = 1 |

**符号接反、控制不生效、力矩不足 三项均已排除**（`out_x=+1` ⇒ `d(avel_p)/dt≈−0.6`，
与旧程序 `d(avel)/dt=−A*u` 一致）。这是**纯阻尼不足**。

```
D 项 = kd_eff * omega  ，输出 clamp 到 ±1
=> 阻尼能力上限  <=>  kd_eff * omega_peak <= 1

旧载具 omega_peak=0.21 => kd_eff 可用 4.68，zeta=0.98（实飞临界阻尼）
本载具 omega_peak=0.96 => kd_eff 只能 1.0，zeta 上限 0.21

要 zeta=0.9 且不饱和：
   kp = alpha*(kd_eff/1.8)^2 = 0.379*(1/1.8)^2 = 0.117
   wn = sqrt(alpha*kp) = 0.21 rad/s（周期 30 s，整段只有 16 s）
=> 【在「绝对角速度 + 固定 clamp」框架内，本载具无解。】
```

### 11.3 定论方案：D 项对物理角速率上限【归一化】

```
omega_phys = sqrt(2 * alpha_now * headroom)     headroom = REF_SLEW_HEADROOM_DEG = 45°
rate       = RATE_D_GAIN * omega / omega_phys
```

实现：`starship_land._att_rate_phys()` + `apply()` 里 ②/④ 两段；日志列 `avel_scale`。

**带来三件事**

1. **解开「kd 被 omega_peak 锁死」的死结。** 绝对模式下 kd_eff 上限是
   `1/omega_peak`，而 omega_peak 恰好是最坏的瞬态 —— 为了让最坏那帧不饱和，
   整趟都在用极弱阻尼。归一化后分母跟着本帧权限走，正常跟踪
   `omega/omega_phys` 只有 0.1~0.3，D 只用掉 1/3 量程，剩下的留给真正的过冲制动。
2. **kd 与载具脱钩。** 归一化后 rate 是「用掉多少比例的物理速率余量」，无量纲。
   kd 的物理含义不再是「rad/s 的倍数」，**换载具不必重算** —— 这正是旧程序
   kd=6 换到本载具必须重算的根本原因，现在被消除了。
3. **自动跟随权限调度。** omega_phys 已随 alpha 变，D 项不必再单独乘 sched
   （sched 仍只作用在 kp）。

> ⚠️ **不要指望它把 zeta 做成常数。** 在「omega 随 alpha 一起涨」的实况下
> （本载具实测 `omega ≈ 0.02*alpha`），
> `zeta_norm = kd*G/(2*sqrt(2h)) * sqrt(omega)/alpha^(3/4)`，
> alpha 11.3→43.7 时 zeta 从 0.16 升到 0.44；而绝对模式计饱和后是 0.39→0.16，
> 正好相反。**归一化把「高油门更差」翻成「低油门更差」**，两端都不理想，
> 但低油门端本来就靠 `TILT_CAP` 收紧 + 小角行程兜住，
> 高油门端才是本趟 `avel_p` 冲到 0.96 的元凶。真正的判据是下面的闭环仿真。

**饱和边界**：`|D| = kd*G*(omega/omega_phys)`，单看 D 自身顶到 1 的门槛是
`omega/omega_phys = 1/(kd*G) = 0.256`。换算成绝对角速率（headroom=45°）：

| alpha | omega_phys | D 饱和门槛 omega |
|---|---|---|
| 11.3（悬停）| 0.557 rad/s (31.9°/s) | 0.143 rad/s |
| 21.7 | 0.771 rad/s (44.2°/s) | 0.198 rad/s |
| 43.7（满推）| 1.095 rad/s (62.7°/s) | 0.280 rad/s |

正常跟踪 `omega` 在 0.05~0.15 rad/s ⇒ D 在 0.25~0.76，**不饱和**。
超过门槛的都是过冲/参考突变瞬态，此时 D 顶满等于**满权限反向制动**，是正确行为
—— 判断是否退化成 bang-bang 要看 `pid_sat_x` 是否**长期**为 1，不能只看单帧 D>1。

**前馈量纲必须一起改**：`_ff_*` 原本是 rad/s，归一化后 D 的 rate 无量纲，
所以 `_ff_*` 也除以同一个 `omega_phys`（见 apply() ④）。漏了这一步等于把前馈放大 3 倍。

```
按物理上限： sqrt(2*alpha_hover*45°) = sqrt(2*10.2*0.785) = 30.2 deg/s   <- 原来取 30
按实测参考速率： 3D 参考 p90 只有 18.6~24.1，p50 只有 10.2~14.5
```

**把护栏设在自己够不到的地方 = 没有护栏。** 实测 `ref_clip` 只有 1~16%，
说明限速器基本没工作过。

现取 **20.0**（= 旧程序实飞可跟踪区间的上沿）。降到 20 后
新 154351 有 5%、新 144058 有 27% 的帧开始被削 —— 与旧程序
「只咬掉最激进少数帧」的口径一致。

### 11.5.3 `TILT_LEAD_SEC` 不能按 1/sqrt(alpha) 外推

**原推导（错的）**：`滞后 ∝ 1/sqrt(alpha)`，`sqrt(0.35/0.0669) = 2.3 倍` ⇒ 取 2.5 s。

**错在哪**：本载具 `alpha` 与旧载具**几乎相同**（16.1~16.4 vs 13.9~18.6 deg/s²），
因为引擎数 9→13、万向节力矩同步涨了 33 倍，正好抵消 `I` 涨的 28 倍。
滞后真正正比于 `sqrt(I/tau)`，而这个比值新旧比 ≈ **1**，不是 2.3。

**更严重的是：前赡在「旋转中的方位参考」上不是补偿，而是主动追更歪的方向。**

| 趟 | 方位参考转速 | 前赡 2.5s 提前量 | 占 az_err 中位 |
|---|---|---|---|
| 旧 164053 | 11.2°/s | 16.8° | 43% |
| 新 144058 | 9.2°/s | 23.0° | 41% |
| **新 154351** | **19.5°/s** | **48.9°** | **78%** |

**⇒ 2.5 s 前赡把姿态目标往误差更大的方向多推了 48.9°。**

现取 **1.5 s**（= 旧程序实测值，也落在旧程序机身滞后 1.2~2.2 s 的区间内）。

### 11.6 换载具时怎么重算

按这个顺序，**每一步都有实测判据**：

1. **先定 kp**：从日志读 `err_x` 中位与 p90，令
   `kp <= 1/(p90_err_rad * sched_max)`。目标是 `pid_sat_x < 15%`。
   **不要按 wn 选。**
2. **再定 kd**：`RATE_D_GAIN` 保持 0.78；kd 按「`kd*0.78*(omega/omega_phys)`
   在正常跟踪时落在 0.4~1.0」选。实测 `avel_scale` 与 `avel_p` 两列可反推比值。
3. **再定 `REF_SLEW_MAX`**：测 3D 参考速率（`tgt_v*` 逐帧反算）的 p90，
   取略高于 p90 的值。**不要用 `sqrt(2*alpha*headroom)` 的物理上限。**
4. **再定 `TILT_LEAD_SEC`**：从 `tilt_act - tilt_cmd` 的时滞回归取实测值，
   **不要按 `1/sqrt(alpha)` 外推**（见 §11.5.3，那条推导漏了 `I` 与力矩同步变化）。
5. **验证列**：`pid_sat_x/z` 长期为 1 = 仍在饱和；`avel_scale` 为 0 = 当帧权限采样
   失败、D 项已退回绝对角速度，分析时需剔除；`ref_clip` 长期为 0 = 限速护栏设得太宽。

## 12. 【必须重算】倾角上限斜率

### 为什么 slope=3.0 对本载具无效

```
alt > 105 m 时 cap = 35.0（打满）
  alt=900 -> 35.0   alt=600 -> 35.0   alt=300 -> 35.0   alt=150 -> 35.0
=> 整个 900~105 m 段，上限【没有任何收紧作用】，纯摆设
```

**旧载具为什么不需要收紧**：`a_cap=86 m/s²`，水平权限 `86*tan(35)=60`，

## 13. 【已修】重解导致推力塌陷

### 现象

每次 `[replan]` 后油门从 0.455 掉到 0.131，持续 0.3~1.3 s。

### 根因

```
t=3.65 replan #2: tf 27.31 -> 24.44
n_i 被【保留】在 15.1（旧修法），但：
  plan_alt 从 739.5 突降到 597.0（跳 -142.5 m）
  真实 alt=717.5，载具比规划点高 120 m
  a_up_raw = p0 + K_VEL*dv + K_POS*(xi0 - h)
           = 3.21 + ... + 0.5*(597-717.5)
           = 3.21 + ... - 60.2  =>  压到 3.30
  油门 0.455 -> 0.131
```

**为什么保留节点号是错的**：`n_i` 是归一化弧长参数，
`frac = n_i/(N-1)`，物理时刻 `t = frac*tf`。
`tf` 一变，同一 `n_i` 对应的物理时刻和高度都变。
而新轨迹是**从当前位置重新规划的**，它的节点 k 与旧轨迹的节点 k 不是同一空间位置。

### 修法

重解后**用当前真实位置在新轨迹上重新投影**：

```python
_n_new = self.find_nearest_index(_xi, self._last_pos, self.prev_vel,
                                float(self.plan['tf']), _N)
self.gfold_n_i = max(0.0, min(float(_N)-2.0, float(_n_new)))
```

与参考仓库的 `n_i = -100` 语义等价，只是避免了那一帧的跳变。
